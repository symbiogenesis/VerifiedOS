# Performance Estimates: What the Security Choices Cost (and Buy) (non-normative)

> Externalized companion to [verification-maximal-os.md](verification-maximal-os.md).
> A **non-normative estimate**, not part of the specification: an engineering-judgment accounting of the performance-relevant features the spec removes, adds, or substitutes, and the resulting net delta.
> Cross-references of the form §N point to sections of that specification.
> Every figure is a **coarse range with wide error bars**, not a benchmark; performance was deliberately subordinated to security (§1), so this document quantifies the accepted price rather than defending it.

## How to read this

- **Baseline.**
  Unless noted, the reference is a **conventional 2026 application-class RISC-V SoC**: out-of-order (OoO) superscalar, TAGE-class dynamic branch prediction, MMU + multi-level TLB, multi-level caches with hardware coherence, aggressive DVFS + turbo, fixed-function GPU and video codecs, RVA23-class ISA *including* the C extension, conventional (non-CHERI) 64-bit pointers, plain DRAM.
  This is "what you would otherwise buy" for the phone/desktop targets the spec addresses.
  **Every figure is scored against that baseline only.** This document does not compare the design to earlier drafts of itself: a mechanism the spec does not contain has no row, and the reasons a mechanism is absent belong to [architectural-alternatives.md](architectural-alternatives.md), not here.
  A **secondary baseline**, a plain *in-order* RV64GC core, is treated in the totals, because against it several of the largest losses vanish.
- **The percentages are per-workload multipliers, NOT additive.**
  Each row is the approximate change *on the workload it applies to*, holding everything else equal. They compound **multiplicatively** and are **gated by workload** (a vector gain and an in-order loss rarely touch the same cycle).
  The totals section is therefore a reasoned synthesis, not a column sum.
- **Recovery levers are scored inside their rows, and a pass the baseline also runs does not cancel one.**
  Where a row states a worse end "scored with X in place", X is a normative lever whose recovery is measured *intra-design* (the same frozen instantiation, un-optimized vs. optimized). Running the same pass on both machines cancels nothing unless the deltas are the same, and they are not: the marginal return of static scheduling and code and data layout is low against an out-of-order core with a dynamic predictor, whose hardware recovers dynamically from whatever the compiler got wrong, and high here, where the compiler is the only latency-hiding mechanism, the only placement mechanism, and the only branch-prediction-recovery mechanism that exists. Wherever the deltas differ, the difference is inter-design gap genuinely closed. What no lever narrows is the residual after every pass has run on both machines: the deleted dynamic mechanisms, booked as this table's accepted costs. Proposals evaluated as recovery levers and rejected are recorded in [architectural-alternatives.md](architectural-alternatives.md) under the recovery gate.
- **Sign convention:** negative = slower than baseline; positive = faster.
  `×` denotes a multiple (e.g. `+900%` = `10×`).

| Core µarch | In-order issue, no speculation/OoO (§2, §15) | Removed | **−35% to −55%** | general scalar / latency-bound | Dominant single factor vs an OoO baseline. **The worse end is scored with the R-18-014e link-step transforms in place; without them the row would run to −60%:** selective inlining, unrolling, and superblock formation on measured hot paths widen the straight-line window the mandatory latency-aware scheduler (R-18-014a) fills, and on this machine that scheduler is the only latency-hiding mechanism that exists, so the transforms' marginal return is high here and small on the baseline, whose OoO window hides the same latency dynamically; the difference is gap closed rather than a pass both machines run. Admission per site is in encoded form under the R-18-014d size constraint, so the row's recovery spends no §15 capacity headroom silently. **The better end does not move:** the transforms reach scheduled straight-line code, not the dependent, branchy scalar work where an OoO window finds ILP no compiler can prove. |
| Core µarch | Static-only branch prediction, no BHT/BTB/RAS (§15) | Removed | **−10% to −30%** | branchy control code | The loss is vs a TAGE-class *dynamic* predictor and is **pipeline-depth-driven, not memory-driven**: a branch costs its fetch-to-resolve distance, which SRAM main memory does not shorten. The retained *static* predictor (backward-taken / forward-not-taken) still resolves loop back-edges (~90%+ on loop-dominated code) at **zero silicon and zero predictor state**, converting the hottest branches from a taken-branch bubble into a correct early redirect. The residual concentrates on **data-dependent** branches, where nothing static helps, but the short non-speculative pipe keeps each mispredict cheap (a few front-end bubbles, not an OoO flush) and `Zicond` (gain row) removes many outright. Deterministic by construction, so it adds **no WCET variance** (§11). Compounds with in-order. **The worse end is scored with the R-18-014e link-step transforms in place; without them the row would run to −30%:** on measured hot paths selective inlining deletes call/return pairs whose returns nothing predicts, and superblock formation straightens the hot trace so the static fall-through guess is right where the baseline's predictor had to learn it; the data-dependent residual is untouched, nothing static helping it, which is what keeps the row open at all. **The absent RAS is also what prices the one code-size lever that adds calls**: outlining's helper return is an indirect branch with nothing predicting it (R-15-036o), which is why that lever is measured on cycles as well as bytes (R-15-036p) rather than taken as free, and why the inlining that deletes such returns and the outlining that adds them are one selectivity decision (R-18-014e), not two. |

| Core µarch | Fixed modest clocks, no turbo/DVFS (§15 power) | Substituted | **−15% to −40% burst; −0% to −15% sustained** | burst/interactive latency | Frequency effect, not IPC; turbo never helps thermally-bound sustained load. |
| Core µarch | No JIT, interpret-only dynamic languages (§2, §14) | Removed | **−60% to −90%** | JS / Wasm / dynamic-language code only | Native AOT code unaffected; hits the browser hardest, and hot numeric Wasm can exceed the range. The row is **mitigated and not erased** by the ahead-of-time interpreter levers §14 admits (R-14-008a): threaded dispatch, an off-device-selected superinstruction set whose bodies are AOT image code and whose size is budgeted (R-14-008b), and data-plane inline caches (R-14-008c). Its scope is narrower than the row's name suggests: the browser's own chrome and privileged JS are image code compiled natively (R-14-008e), and a web application that ships through the §13 install path pays none of it (R-14-008f). |
| ISA substituted | No C / compressed extension; code encoded in the fixed-rate **dictionary format** instead (§15, R-15-036a) | Substituted | **≈0% to +3%** | fetch-bound | **This row is a small gain where excluding `C` alone would be the design's largest code-size loss, and it is a substitution rather than a recovery.** `C` is excluded on its own ground (no overlapping 16-bit-aligned decodings, no decode ambiguity for the binary-level proofs), but the density it was wanted for is supplied by a fixed-width-slot dictionary encoding that *deletes* variable-length fetch, mid-instruction reinterpretation, and the alignment-fragment machinery rather than mitigating them. Sizing: the encoding lands at **60% to 70% of the canonical 32-bit stream** at dictionary hit rates of 0.95 down to 0.80, counting both the slot term (R-15-036h) and the escape-packing term (R-15-036j), against the central ~72% an RVC baseline gets, so this machine's image is **2% to 16% smaller than that central RVC comparator's**, against the 33–43% larger it would be with `C` excluded and nothing supplied in its place. **That is a claim about *p* with two baseline-sensitive sign boundaries:** *p* = 0.773 is break-even against the central 72% comparator, while the conservative claim against an optimistic 70% RVC result fails below *p* = 0.804 (R-15-036j, R-15-036k), which is why *p* is measured stratified by operand class rather than quoted as an aggregate and why the emitted call and global-address forms are a freeze-time decision (R-15-036l). `Zcmt`'s JVT mechanism is **not** an unbooked extra gain: it is excluded at R-15-036q, and no separate debit is scored because the stated RVA23/RVC baseline supplies no JVT call path. The retained direct absolute-target candidate performs no table read; its density effect enters only through the measured *p*, and no cycle gain is credited before that freeze measurement. **One residual is named here rather than netted in:** the encoding cannot collect the *sequence* class, a dictionary entry being one instruction, so prologue and epilogue idioms survive it. The saves that make them up are stereotyped and already hit, though, so a compound multi-save is worth (*k* − 1) slots and not (*k* − 1) instructions, half what the same instrument is worth upstream; `Zcmp`'s own restartable form is refused on structure (R-15-036m), and the all-or-nothing single-check form is a freeze-time candidate expected to be dropped (R-15-036n). Neither is scored above, and this row moves only if that measurement carries it. **The general form of that residual is taken in software rather than left open, and it is the one code-size lever on this page that spends cycles to buy bytes.** A recurring *region* is out of reach of a dictionary index and of a named idiom alike, so it is collected by outlining and tail merging in the backend, intra-compartment and only where the region needs no frame of its own (R-15-036o). Both directions are worth more here than on the baseline that ships the same `-Oz` pass, and they point opposite ways: the byte win is worth more because the image is a hard on-die capacity quantity with no I-cache, and the cycle cost is worse because the helper's return is an indirect branch this machine predicts with nothing (the no-RAS row above) and because a partition's capacity is its slot width, so worst-case inflation widens a slot or does not fit. Its size is also not a property of the pass alone: for a region of *n* instructions at *m* sites the inline cost is *nm* slots against *n* + *m* + 1 outlined under a composition-time absolute call and *n* + 2*m* + 1 under a PC-relative one, so break-even moves with R-15-036l's decision and a two-instruction region never pays under the PC-relative form. **Nothing here is scored either**: R-15-036p makes it a two-axis measurement, bytes removed and worst-case cycles added, taken *before* the candidates above so their corpus comes from a backend that already outlines. Expect it to carry where the general-scalar rows below do not notice it, low single digits of image on ordinary code and more on a repetitive composed roster, since the axis it is refused on is the one it is measured against. Fetch bandwidth moves with it: fewer bits per instruction than the baseline, at a fixed per-bundle latency with no I-cache, no predictor, and no decompression table. The two code-size *additions* the profile makes (capability indexed load/store, bitfield extract/insert) are scored in the gain rows below and are **not** netted here. Booked on the other side of the ledger: constant-time balancing is restated over encoded bundle count (R-15-036f), and the dictionary is a permanent freeze-time commitment (R-15-036i). |
| ISA removed | Fixed-latency integer DIV and vector FPU, no early-out, subnormal-safe (§15) | Substituted | **−1% to −6%** | divide / sqrt / FP-heavy | Price of the constant-time mandate. |
| ISA removed | No scalar `F`/`D`, scalar float folded onto the vector FPU (§15) | Substituted | **−2% to −20%** | scalar-float-bound code | VL=1 vector ops + soft-float-register ABI setup; dependent scalar-FP chains (recurrences, running sums) set the worse end, the vector FPU's longer fixed latency being unhideable inside them; well-vectorized FP is unaffected (runs on RVV). |
| ISA removed | No prefetch / non-temporal hints, Zicbop/Zihintntl (§15) | Removed | **≈0%** | memory-bound streaming | **No downside in this design.** A prefetcher exists to hide DRAM round-trips by warming a cache ahead of demand; this machine has **neither a cache nor DRAM**, so it has nowhere to place data, and the flat-SRAM load-use latency that remains is hidden instead by **static instruction scheduling** on the exposed-ILP in-order pipe (the compiler's job, not a prefetcher's). Any latency-bound cost is already booked under the no-cache / SRAM rows below; scoring it here would **double-count**. Streaming is bandwidth-bound, which a prefetcher does not help. Explicit loads only. **What the front end does keep is not a prefetcher, and it is part of why this row is ≈0% rather than a loss**: a run-ahead **static-path fetch buffer** (R-15-165) fetches the statically determined successor of instructions already fetched, fall-through or the backward-taken / forward-not-taken target of an already-decoded branch, so decode stays fed at the flat-SRAM latency. It is separated from a prefetch engine by **table-freeness** and not by depth: it holds no structure indexed by or updated from prior execution, so its request sequence is a function of the instruction stream alone, it carries nothing history-dependent across a partition switch, and the audit that decides the absence contract is a table search rather than a judgment call. |
| ISA removed | Misaligned accesses trap (§15) | Substituted | **−0% to −5%** | code with unaligned access | Well-aligned code ≈ 0. |
| ISA removed | `Zaamo`-only, no LR/SC, no CAS (§15) | Removed | **−0% to −3%** | lock-free / atomic-heavy | The loss is the absence of lock-free *CAS*, not slower atomics: the retained `Zaamo` (gain row below) still resolves the real RMW traffic (refcounts, status flags) in one instruction. Spec argues no lock-free multi-writer consumer exists above a share-nothing kernel (§7); near-zero in practice. |
| Mem / security | CHERI purecap, **64+1-bit** capabilities (§5, §7, §8, §15) | Added | **≈0% to −3%** | pointer-heavy | **The pointer-width term that dominates this row on a 128-bit format is largely absent.** A capability is 64 bits over a 36-bit address space (R-15-007, R-15-002a), the same width as the baseline's plain pointer, so the footprint and bandwidth penalty a 128-bit format charges on every pointer-dense structure, spill, and argument does not arise; what remains is the metadata-manipulation traffic (`csetbounds`, `cincoffset`, seal/unseal) that has no baseline counterpart, partly self-funded by the fusion and indexed-load/store rows below, plus the tag plane, which is ≈0% in time and 1.56% in array area (row below). R-05-149a still deletes redundant interior capabilities where authority and lifetime are already shared, but at 64 bits that saves half what it would at 128. The **capacity** effect is the larger one and is not a percentage: on a machine whose main memory is a hard on-die SRAM budget (§15), halving every resident capability is roster headroom, and halving capability spills is image size, compounding with rather than offsetting the dictionary-encoding row above. Booked on the other side of the ledger, not scored here: bounds are byte-exact only to 256 bytes (R-15-007c). |
| Mem / security | CHERI native tag bits in SRAM (§15) | Added | **≈0%** | pointer-dense | Bespoke SRAM carries the 1-bit-per-granule CHERI validity tag natively in the word, read in parallel with the data, so the reserved-memory tag table and tag cache a tag-less DRAM forces (with their miss-and-walk traffic) are deleted; only a small SRAM-width overhead remains, no latency term. The granule follows the capability width and is **64 bits** (R-15-203), so the plane is 1.56% of the array rather than 0.78% and its DECTED area doubles; the ECC codeword is unchanged at 128 data bits carrying two tag bits, so no data-side check-bit area moves and the row stays ≈0% in time. Against the doubled plane, the capability-dense structures the array mostly holds halve. **It is one plane and not two, which is the larger area fact on this row:** the Write-before-Read **initialization-tag plane** a second metadata plane would have carried is excluded (R-15-035), so no second bit per granule, no second DECTED coverage, no second Sail invariant, and no second RTL obligation enter here. The property it would have carried is taken by the §5 definite-initialization type attribute instead, which is *more* precise than the plane rather than a weaker stand-in: it decides sub-object partial initialization and stack-frame-local initialization, the two cases a granule-indexed plane misses at its default granularity and could buy back only with per-byte silicon. |
| Mem / security | Temporal safety: revocation load filter, sized sidecar, and the budgeted sweep with `cloadtags` (§8, §15, R-15-007q) | Added | **≈0% on the load path; ≈0% to −3% of system capacity** | any workload that frees memory; the cost lands in composition, not in a hot loop | **The load path is the half that is genuinely free, and the sweep is the half that is a capacity charge rather than a multiplier.** Every tagged capability load checks a bank-side revocation bitmap slice indexed by the loaded capability's base, read in parallel with the data and the validity tag, emitting no second fabric or main-memory transaction and admitting no retry (R-08-005, R-08-005a): one fixed latency whether the bit is clear or set, so it is ≈0% in time and enters no WCET entry as a variable term. What it costs instead is array, one ECC-protected bit per 8-byte granule over the composition-fixed revocable intervals, charged by the static memory plan against the same SRAM budget as the tag plane above and a **capacity** quantity rather than a percentage. **The sweep is on no workload's critical path and is not scored as one:** containment is the epoch flip (R-08-006), and reclamation runs as an incremental preemptible task in its own §11-admitted background slot class, per core, sized at composition, never in another partition's time (R-08-007). The system column is therefore the share of a core's frames that class takes, a composition property with a floor of zero, and mis-sizing it delays reclamation of the requester's *own* quarantined memory rather than perturbing any hard task's schedule (R-08-008). **`cloadtags` is what sizes it, and its saving is bounded rather than dramatic**: the inspection loop spends one instruction per granule group where it otherwise spends a capability load and a tag test per granule, a saving of the group size on an all-clear group and of one instruction on a full one (R-15-007q). It is **not** a memory-traffic saving, and that is where this platform parts from the upstream argument for the instruction: native tag bits share the array row with the data and are read in parallel with it (R-15-203), so a tag-only read activates what a data read would and buys no bank cycle. What it buys is the sweep's quantum, and what the quantum buys is a composition-time trade between a narrower background slot class and a shorter quarantine before a revoked granule returns to service (R-08-007a). Booked on the other side of the ledger and not scored here: the two alternatives that would have moved this row further are declined elsewhere, the revocation colour as a capability field the 64-bit budget has no room for (R-08-004b) and the CHERIoT-Ibex TBRE engine as an autonomous memory-touching walker (R-08-009), so the walk is software by choice and this instruction is the whole of what accelerates it. The row lands as **capacity and not as any archetype's multiplier**, which is why the totals below are unchanged by it. |
| Mem / security | No memory-path cryptography (§15) | Removed | **≈0%** | n/a | The die is the trust boundary and main memory is on it, so the memory controller applies **no encryption and no integrity construction**: no cipher stage, no authentication tag, no counter tree, and no on-die structure to hold either. Where a conventional part pays controller latency for memory encryption, this design pays nothing, because the interface such a mechanism protects does not exist (§15, §17). The controller's only pipeline terms are the granule read-modify-write and the ECC encode/check below. |
| Mem / security | ECC across all SRAM: main memory and on-die arrays (§15, §16) | Added | **−1% to −4%** | memory-bound | Every SRAM array (main memory, register files, scratchpads, native tag bits; there are no data caches) carries SECDED, DECTED on the capability-critical bits, with interleaving and scrubbing; correction is off the critical path, so the added cost is mostly SRAM check-bit area plus a small scrub-bandwidth share. |
| Mem / security | SRAM main memory replaces DRAM (§15) | Substituted | **+2% to +30%** | memory-latency-bound / pointer-chasing | SRAM's far lower array-access latency, higher bandwidth, and absence of activate/precharge/refresh stalls beat the *conventional DRAM* baseline; this is a **memory-technology gain, not one the security architecture confers**, so it is scored only against that baseline and **would not appear against a comparable SRAM-equipped conventional system** (which would share it); distinct from the no-MMU/no-TLB lever. The tradeoff is much lower capacity and higher idle leakage (§15), not speed, the leakage paid down by the static cell levers (row below). Capacity comes from **sequential-3D tiers on the one die**, whose inter-tier vias are far shorter and denser than the microbumps of a chiplet or bonded stack, so the tier-to-controller path is *faster* than those alternatives would give; against that, sequential 3D's low-temperature upper-tier processing caps the array's own device speed and the shared heat path tightens sustained-power headroom, making the net mixed rather than a clean win. **The tier count behind that capacity is two-case rather than a continuum, and the second case is not a smaller version of the first** (R-15-173a): where complementary back-end devices reach array-grade quality and manufacturable scale, tier count is an ordinary yield-and-cost question and this row reads as written; where they do not, the vertical lever is **absent rather than reduced**, capacity is the single planar tier at order 1 to 2 GB, and the roster is fit to that budget or refused at admission, there being no swap and no overcommit (R-15-171). Capacity is the only quantity the branch decides; the latency and bandwidth figures above do not move. |
| Mem / security | Low-leakage SRAM cell levers: static body bias, high-Vt core, gate-length bias, retentive gating (§15) | Added | **−0% to −3%** | memory-latency-bound / post-idle-wake | The bespoke SRAM's booked idle-leakage cost (§15) is paid down by *static* cell levers (a high-Vt storage core with a low-Vt periphery, a static reverse body or well bias, gate-length biasing, and state-retentive sleep-transistor gating of idle banks). The win is **idle/standby power, a battery-life gain not a compute-% multiplier scored here**; the active cost is small, the low-Vt periphery keeping the access path fast so the high-Vt core and gate-length delay add little (an *all*-ultra-high-Vt array would instead slow the periphery-bound access path by roughly a fifth to a half and give back the SRAM latency gain, which is why the split is asymmetric), plus a fixed per-domain transition latency when a gated array is brought back, taken at a global mode boundary and **never on an access** (the power-gating row below). The **body-bias lever applies to the logic tier only**, the sequential-3D memory tiers having no back gate (§15), so the array's leakage rests on the asymmetric-Vt, gate-length-biasing, and retentive-gating subset and this row is correspondingly at the weaker end for memory. Sub-threshold is declined for the active set (it would forfeit the SRAM speed the rows above credit) and kept only for idle-bank retention; the dynamic, data-dependent variants (workload-tracking body bias, activity-driven gating, adaptive assist) are declined as a data-dependent power channel (§15). A tier that picks a multi-port (8T/9T/10T) cell for stability or minimum voltage trades **density first and latency conditionally**: reported layouts run ~1.67× the 6T cell for a single decoupled read port and up to ~3.18× for two, and the single-ended read buffer needs a larger sense swing than differential small-signal sensing, so speed is held only by segmenting columns and spending the periphery area to do it. It buys **no** side-channel benefit and on the leakage-analysis axis is a regression, which is why it is admitted only where multiple ports are functionally required and never as a security lever ([Evaluated Architectural Alternatives](architectural-alternatives.md)). |
| Mem / security | Composition-time SRAM power gating: ON / RETAINED / OFF domains per global mode (§15, R-15-189a, R-15-189d, R-15-189j) | Added | **≈0% in-slot; one fixed §11 mode-transition term** | mode changes and standby entry/exit; the return is idle energy, not a compute-% | **The mechanism that takes the leakage cost the row above only pays down, and it is scored as a transition constant because nothing about it reaches a running partition.** Arrays holding nothing in a mode are retained or collapsed by the same RoT-attested transition that installs the mode (R-15-189a), and **static allocation is what makes the unused set knowable**: with no allocator, no swap, no overcommit, and no demand growth, the whole-program memory plan's slot assignment is the complete and final statement of which bytes an admitted composition can reach (R-15-189b). A domain's state is a function of the **mode index alone** (R-15-189m), so the rail sequencing, the fixed dwell times, and the unconditional OFF→ON array clear (zero data, cleared validity tags, regenerated SECDED and DECTED for both planes, R-15-189j) are data-independent modeled constants folded into the §11 mode-transition budget, adding a term to that budget and **no variability to any partition's WCET**. **There is no wake-on-access anywhere in the mechanism, which is why this is not a memory-path latency tail** (R-15-189h): RETAINED is state-retentive and **not addressable**, OFF has had the rail collapsed outright, and an access decoding to a non-ON domain is a fail-stop sentinel event (§16), never a floating read, never a stall, and never a demand power-up, that being demand paging with a power rail. Idle-timer, watermark, and access-counter gating are declined with it, each rebuilding the workload-to-power-state feedback loop §15 deletes. What it buys is **on the energy axis and not on this table's**: leakage is proportional to powered bitcell count (R-15-189l), so the island-exclusivity partitioning tax stays a capacity tax and stops being a leakage tax, a deployment leaks for the roster it composed rather than for the capacity fabricated, and standby leaks in proportion to the one live island rather than the fabricated array (R-15-190). Booked on the other side of the ledger and inside the transition term, not scored separately: background scrubbing runs on ON domains only, so a mode holding a domain RETAINED past the §16 accumulation bound owes either a periodic ON scrub interval or a full verify-and-correct sweep on the exit path before admission (R-15-189k). |
| Mem / security | Capability-checked DMA, no IOMMU/IOPMP (§15) | Added | **−0% to −3%** | DMA / I/O-heavy | Capability-bounds + tag check at the fabric; no page-table walk (lighter than an IOMMU); externally corroborated by CapChecker's measured ~1.4% for boundary capability-checking on heterogeneous accelerators (Cheng, Markettos et al., ISCA 2025). |
| Mem / security | Device-space stores non-bufferable: drain-then-issue, accept-before-retire (§15, R-15-015b) | Added | **≈0% general; −0% to −3%** | MSI / cross-core notification, MMIO-heavy device setup | A device store leaves the core only after the store buffer has drained and completes at the endpoint before retiring, so it pays a drain plus a fabric round-trip where a posted write would have paid neither. **Not optional and not bought for performance:** it is what keeps `fence.t`'s padded constant a function of the partition class rather than of the slowest endpoint the outgoing partition touched (R-15-218), and what keeps SRAM-store→device-store inside TSO (R-15-015). Cost is concentrated rather than diffuse: MMIO configuration is cold-path by construction (R-15-140) and doorbells are per-batch under R-11-010's ring-depth amortization, leaving the **MSI send** (interrupt-send being a store to an interrupt file, R-15-064, R-08-032) as the one class paying at rate, mitigated by the same batching-at-the-source the ring-window layout mandates (R-15-223a). The round-trip is bounded and static under TDM arbitration (R-15-225) and terminates in the endpoint's island-clock FIFO (R-15-196), so the typical accept is fabric-rate and enters §11 as a known constant rather than as variance; only a **full** FIFO degrades it to the link's own rate, which is the case R-11-010's depth sizing already governs. **The term is confined to the compartments that actually own a slow endpoint**, because device authority is provisioned by latency class (R-15-015c): a grant does not span a fabric-rate register block and a divided-clock endpoint, so the slow endpoint prices its own thin driver compartment's slot and nobody else's, and the split is taken only where that endpoint dominates the bound (R-15-015d). Partly self-funding: with R-15-015a's destination set extended to device endpoints it makes every device ordering edge structural, retiring the device consumer of `fence` and leaving only userspace store→load synchronization as a possible drain consumer. |

## Headline total

- **General-purpose scalar / interactive code: ≈ −55%, range −45% to −70%** vs a conventional out-of-order RISC-V application core.
  Ordinary software *feels like* it runs at roughly **a third to a bit over half** the speed of what you would otherwise buy: the deliberate, spec-wide price of deleting speculation, dynamic prediction, reactive clocking, and the cache hierarchy, and of paying the CHERI, partitioning, and static-scheduling taxes.
  The memory path contributes little to that figure, carrying ECC and bank partitioning but no cryptographic stage at all.
- **The workloads the machine is built for, vector graphics/DSP, symmetric crypto, and matrix/AI, run at parity-to-many-times the baseline** (roughly **+3× to +100×** over a scalar baseline, depending on class), because RVV, the systolic units, and table-free crypto more than repay the scalar overheads whenever the work vectorizes.
  **The one exception inside that set is public-key crypto**, where deleting the superoptimizer route leaves handshake-path field arithmetic at verified-C speed (archetype table above): a connection-setup cost, not a bulk-throughput one.
- **Blended "typical desktop/phone" experience:** dominated by the scalar/interactive figure for responsiveness (**−45% to −70%**), with the accelerated paths pulling media, symmetric crypto, radio/DSP, and AI inference back to parity-or-better, and networking capped by the gigabit wired ceiling rather than slowed below it (big table).
  Net: a machine that is **materially slower for general use and faster for the parallel workloads it targets**, exactly the trade §1–§2 declare.

### Sensitivity to the baseline

If the reference core is instead taken to be a **plain in-order RV64GC core** (the common shipping RISC-V application profile, dynamic prediction, MMU, DVFS, C extension, non-CHERI, no vector) rather than an OoO part, then two of the largest losses (in-order vs OoO, and much of the turbo gap) **disappear or shrink**, while the no-MMU, bit-manip, and CFI/ASLR gains and the vector/crypto/matrix gains remain.
**What does *not* shrink is the memory side.** An RV64GC part has a cache hierarchy, unpartitioned banks, a conventional interconnect, and scalar `F`/`D`, so the no-cache row (−10% to −40%), the bank-partitioning (−5% to −15%) and TDM-NoC (−5% to −10%) rows, and the no-scalar-float row (−2% to −20%) all apply against it **in full**. Swapping baselines retires the *core* rows, not the memory and isolation rows, and after the in-order term is removed the no-cache row becomes the largest single loss that remains.
Against that baseline:

- **General scalar: ≈ −20% to −60%** (static prediction, the flat cacheless hierarchy, bank/NoC partitioning, CHERI, and no scalar `F`/`D`, minus the single-address-space, bit-manip, fusion, dictionary-encoding, and SRAM gains, and minus the same static-layout recovery, which applies against this baseline too but returns less against it, an RV64GC part having a cache that was already doing the placement).
  The range is wide because it is **set almost entirely by cache residency**: a workload whose working set the baseline's cache was already holding pays the no-cache row at close to its full −40%, while one that streams or fits in the island's banks pays near zero there and lands at the optimistic end.
- **Vector / crypto / matrix: unchanged, still large net positives**, and larger still because a plain RV64GC baseline has no vector unit to compare against.

So the design's general-purpose penalty is **"roughly half"** against a premium OoO core and **"a fifth to well over half, depending on cache residency"** against an ordinary in-order core, and in both cases it *wins* on the parallel and cryptographic workloads it was built to run.
The in-order baseline is a *narrower* penalty, not a small one: deleting the cache hierarchy costs the same against a modest core as against a premium one.

A second baseline axis is **memory technology**.
Both reference baselines above use DRAM, so the SRAM main-memory row (the big table) scores as a gain; against a hypothetical conventional system that also used SRAM main memory that gain would vanish.
What the security architecture actually contributes on the memory axis is the *deletion* of the refresh, RowHammer, and PRAC machinery (§15), which simplifies the design rather than costing performance.
SRAM's mirror cost on that axis is higher idle leakage (§15), an energy effect rather than a throughput one and so not scored as a compute-% above.
Two levers pay it down and they act on different quantities: the static, composition-time **cell** levers (the low-leakage row), whose only compute-axis footprint is the small active-access cost booked there, and **composition-time power gating** (the gating row), which is the larger of the two because it changes the bitcell count rather than the per-cell coefficient. Leakage being proportional to powered bitcell count (R-15-189l), collapsing the arrays a mode does not use means a deployment leaks for the roster it composed rather than for the capacity fabricated, and standby leaks in proportion to the one live island. Neither lever is reactive: the dynamic and data-dependent techniques, workload-tracking body bias, activity-driven gating, idle-timer and access-counter bank gating, and wake-on-access, are declined together as a power side channel and a workload-to-power-state feedback loop.
