# Performance Estimates: What the Security Choices Cost (and Buy) (non-normative)

> Externalized companion to [verification-maximal-os.md](verification-maximal-os.md).
> This is a **non-normative estimate**, not part of the specification: an engineering-judgment accounting of the performance-relevant features the spec removes, adds, or substitutes, and the resulting net delta.
> Cross-references of the form §N point to sections of that specification.
> Every figure is a **coarse range with wide error bars**, not a benchmark; performance was deliberately subordinated to security (§1), so this document quantifies the accepted price rather than defending it.

## How to read this

- **Baseline.**
  Unless noted, the reference is a **conventional 2026 application-class RISC-V SoC**: out-of-order (OoO) superscalar, TAGE-class dynamic branch prediction, MMU + multi-level TLB, multi-level caches with hardware coherence, aggressive DVFS + turbo, fixed-function GPU and video codecs, RVA23-class ISA *including* the C extension, conventional (non-CHERI) 64-bit pointers, plain DRAM.
  This is "what you would otherwise buy" for the phone/desktop targets the spec addresses.
  **Every figure is scored against that baseline only.** This document does not compare the design to earlier drafts of itself: a mechanism the spec does not contain has no row, and the reasons a mechanism is absent belong to [architectural-alternatives.md](architectural-alternatives.md), not here.
  A **secondary baseline**, a plain *in-order* RV64GC core, is treated in the totals, because against it several of the largest losses vanish.
- **The percentages are per-workload multipliers, NOT additive.**
  Each row is the approximate change *on the workload it applies to*, holding everything else equal. They compound **multiplicatively** and are **gated by workload** (a vector gain and an in-order loss rarely touch the same cycle).
  The totals section is therefore a reasoned synthesis, not a column sum.
- **Sign convention:** negative = slower than baseline; positive = faster.
  `×` denotes a multiple (e.g. `+900%` = `10×`).

## The big table

| Group | Feature (spec §) | Change | Est. Δ perf | Applies to | Notes |
|---|---|---|---|---|---|
| Core µarch | In-order issue, no speculation/OoO (§2, §15) | Removed | **−35% to −60%** | general scalar / latency-bound | Dominant single factor vs an OoO baseline. |
| Core µarch | Static-only branch prediction, no BHT/BTB/RAS (§15) | Removed | **−10% to −30%** | branchy control code | The loss is vs a TAGE-class *dynamic* predictor and is **pipeline-depth-driven, not memory-driven**: a branch costs its fetch-to-resolve distance, unaffected by SRAM main memory, so the "no long DRAM round-trips" argument does **not** apply here. The retained *static* predictor (backward-taken / forward-not-taken) still resolves loop back-edges (~90%+ on loop-dominated code) at **zero silicon and zero predictor state**, converting the hottest branches from a taken-branch bubble into a correct early redirect. The residual concentrates on **data-dependent** branches, where nothing static helps, but the short non-speculative pipe keeps each mispredict cheap (a few front-end bubbles, not an OoO flush) and `Zicond` (gain row) removes many outright. Deterministic by construction (no predictor-state variance), so it adds **no WCET variance** (§11). Compounds with in-order. |
| Core µarch | No SMT (§15) | Removed | **0%; −13% to −23%** | multithreaded throughput only | No single-thread effect. The loss is the *inverse* of the throughput SMT adds: 2-way SMT typically gains 15–30%, so removing it costs `1 − 1/1.15` to `1 − 1/1.30`. |
| Core µarch | Fixed modest clocks, no turbo/DVFS (§15 power) | Substituted | **−15% to −40% burst; −0% to −15% sustained** | burst/interactive latency | Frequency effect, not IPC; turbo never helps thermally-bound sustained load. |
| Core µarch | No JIT, interpret-only dynamic languages (§2, §14) | Removed | **−60% to −90%** | JS / Wasm / dynamic-language code only | Native AOT code unaffected; hits the browser hardest. The row is **mitigated and not erased** by the ahead-of-time interpreter levers §14 now admits (R-14-008a): threaded dispatch, an off-device-selected superinstruction set whose bodies are AOT image code and whose size is budgeted (R-14-008b), and data-plane inline caches (R-14-008c). None is runtime codegen and no interpreter matches a JIT, so the figure stands as the accepted cost of W^X on the delivery path. Its scope is narrower than the row's name suggests: the browser's own chrome and privileged JS are image code compiled natively (R-14-008e), and a web application that ships through the §13 install path pays none of this at all (R-14-008f). |
| ISA substituted | No C / compressed extension; code encoded in the fixed-rate **dictionary format** instead (§15, R-15-036a) | Substituted | **≈0% to +3%** | fetch-bound | **This row used to be the design's largest code-size loss and is now a small gain, and the reversal is a substitution rather than a recovery.** `C` stays excluded on its original ground (no overlapping 16-bit-aligned decodings, no decode ambiguity for the binary-level proofs), but the density it was wanted for is supplied by a fixed-width-slot dictionary encoding that *deletes* variable-length fetch, mid-instruction reinterpretation, and the alignment-fragment machinery rather than mitigating them. Sizing: the encoding lands at **60% to 70% of the canonical 32-bit stream** at dictionary hit rates of 0.95 down to 0.80, counting both the slot term (R-15-036h) and the escape-packing term (R-15-036j), against the ~72% an RVC baseline gets, so this machine's image is **2% to 16% smaller than the RVC-carrying baseline's**, where it was formerly 33–43% larger. **That is a claim about *p* and it inverts at *p* = 0.773**: below that hit rate the image is *larger* than the RVC baseline's and this row turns back into the loss it used to be, which is why *p* is measured stratified by operand class rather than quoted as an aggregate (R-15-036k) and why the emitted call and global-address forms are a freeze-time decision (R-15-036l). **One residual is named here rather than netted in:** the encoding cannot collect the *sequence* class, a dictionary entry being one instruction, so prologue and epilogue idioms survive it. The saves that make them up are stereotyped and already hit, though, so a compound multi-save is worth (*k* − 1) slots and not (*k* − 1) instructions, half what the same instrument is worth upstream; `Zcmp`'s own restartable form is refused on structure (R-15-036m), and the all-or-nothing single-check form is a freeze-time candidate expected to be dropped (R-15-036n). Neither is scored above, and this row moves only if that measurement carries it. Fetch bandwidth moves with it: fewer bits per instruction than the baseline, at a fixed per-bundle latency with no I-cache, no predictor, and no decompression table. The two code-size *additions* the profile makes (capability indexed load/store, bitfield extract/insert) are scored in the gain rows below and are **not** netted here. Booked against the gain, on the other side of the ledger: constant-time balancing is restated over encoded bundle count (R-15-036f), and the dictionary is a permanent freeze-time commitment (R-15-036i). |
| ISA removed | Fixed-latency integer DIV and vector FPU, no early-out, subnormal-safe (§15) | Substituted | **−1% to −6%** | divide / sqrt / FP-heavy | Price of the constant-time mandate. |
| ISA removed | No scalar `F`/`D`, scalar float folded onto the vector FPU (§15) | Substituted | **−2% to −15%** | scalar-float-bound code | VL=1 vector ops + soft-float-register ABI setup; well-vectorized FP is unaffected (runs on RVV). |
| ISA removed | No prefetch / non-temporal hints, Zicbop/Zihintntl (§15) | Removed | **≈0%** | memory-bound streaming | **No downside in this design.** A prefetcher exists to hide DRAM round-trips by warming a cache ahead of demand; this machine has **neither a cache nor DRAM**, so it has nowhere to place data, and the flat-SRAM load-use latency that remains is hidden instead by **static instruction scheduling** on the exposed-ILP in-order pipe (the compiler's job, not a prefetcher's). Any latency-bound cost is already booked under the no-cache / SRAM rows below; scoring it here would **double-count**. Streaming is bandwidth-bound, which a prefetcher does not help. Explicit loads only. |
| ISA removed | Misaligned accesses trap (§15) | Substituted | **−0% to −5%** | code with unaligned access | Well-aligned code ≈ 0. |
| ISA removed | `Zaamo`-only, no LR/SC, no CAS (§15) | Removed | **−0% to −3%** | lock-free / atomic-heavy | The loss is the absence of lock-free *CAS*, not slower atomics: the retained `Zaamo` (gain row below) still resolves the real RMW traffic (refcounts, status flags) in one instruction. Spec argues no lock-free multi-writer consumer exists above a share-nothing kernel (§7); near-zero in practice. |
| Mem / security | CHERI purecap, **64+1-bit** capabilities (§5, §7, §8, §15) | Added | **≈0% to −3%** | pointer-heavy | **The pointer-width term is what this row used to be, and it is largely gone.** A capability is 64 bits over a 36-bit address space (R-15-007, R-15-002a), the same width as the baseline's plain pointer, so the footprint and bandwidth penalty a 128-bit format charged on every pointer-dense structure, spill, and argument does not arise; what remains is the metadata-manipulation traffic (`csetbounds`, `cincoffset`, seal/unseal) that has no baseline counterpart, partly self-funded by the fusion and indexed-load/store rows below, plus the tag plane, which is ≈0% in time and 1.56% in array area (row below). R-05-149a still deletes redundant interior capabilities where authority and lifetime are already shared, but it now saves half of what it used to. The **capacity** effect is the larger one and is not a percentage: on a machine whose main memory is a hard on-die SRAM budget (§15), halving every resident capability is roster headroom, and halving capability spills is image size, compounding with rather than offsetting the dictionary-encoding row above. Booked cost, on the other side of the ledger and not scored here: bounds are byte-exact only to 256 bytes (R-15-007c). |
| Mem / security | CHERI native tag bits in SRAM (§15) | Added | **≈0%** | pointer-dense | Bespoke SRAM carries the 1-bit-per-granule CHERI validity tag natively in the word, read in parallel with the data, so the reserved-memory tag table and tag cache a tag-less DRAM forces (with their miss-and-walk traffic) are deleted; only a small SRAM-width overhead remains, no latency term. The granule follows the capability width and is **64 bits** (R-15-203), so the plane is 1.56% of the array rather than 0.78% and its DECTED area doubles; the ECC codeword is unchanged at 128 data bits carrying two tag bits, so no data-side check-bit area moves and the row stays ≈0% in time. Against the doubled plane, the capability-dense structures the array mostly holds halve. |
| Mem / security | No memory-path cryptography (§15) | Removed | **≈0%** | n/a | The die is the trust boundary and main memory is on it, so the memory controller applies **no encryption and no integrity construction**: no cipher stage, no authentication tag, no counter tree, and no on-die structure to hold either. Where a conventional part pays controller latency for memory encryption, this design pays nothing, because the interface such a mechanism protects does not exist (§15, §17). The controller's only pipeline terms are the granule read-modify-write and the ECC encode/check below. |
| Mem / security | ECC across all SRAM: main memory and on-die arrays (§15, §16) | Added | **−1% to −4%** | memory-bound | Every SRAM array (main memory, register files, scratchpads, native tag bits; there are no data caches) carries SECDED, DECTED on the capability-critical bits, with interleaving and scrubbing; correction is off the critical path, so the added cost is mostly SRAM check-bit area plus a small scrub-bandwidth share. |
| Mem / security | SRAM main memory replaces DRAM (§15) | Substituted | **+2% to +30%** | memory-latency-bound / pointer-chasing | SRAM's far lower array-access latency, higher bandwidth, and absence of activate/precharge/refresh stalls beat the *conventional DRAM* baseline; this is a **memory-technology gain, not one the security architecture confers**, so it is scored only against that baseline and **would not appear against a comparable SRAM-equipped conventional system** (which would share it); distinct from the no-MMU/no-TLB lever. The tradeoff is much lower capacity and higher idle leakage (§15), not speed, the leakage paid down by the static cell levers (row below). Capacity comes from **sequential-3D tiers on the one die**, whose inter-tier vias are far shorter and denser than the microbumps of a chiplet or bonded stack, so the tier-to-controller path is *faster* than those alternatives would give; against that, sequential 3D's low-temperature upper-tier processing caps the array's own device speed and the shared heat path tightens sustained-power headroom, making the net mixed rather than a clean win. |
| Mem / security | Low-leakage SRAM cell levers: static body bias, high-Vt core, gate-length bias, retentive gating (§15) | Added | **−0% to −3%** | memory-latency-bound / post-idle-wake | The bespoke SRAM's booked idle-leakage cost (§15) is paid down by *static* cell levers (a high-Vt storage core with a low-Vt periphery, a static reverse body or well bias, gate-length biasing, and state-retentive sleep-transistor gating of idle banks): the win is **idle/standby power, a battery-life gain not a compute-% multiplier scored here**, at a small active cost, the low-Vt periphery keeping the access path fast so the high-Vt core and gate-length delay add little (an *all*-ultra-high-Vt array would instead slow the periphery-bound access path by roughly a fifth to a half and give back the SRAM latency gain, which is why the split is asymmetric), plus a wake latency on re-activating a retention-gated idle bank; note that the **body-bias lever applies to the logic tier only**, the sequential-3D memory tiers having no back gate (§15), so the array's leakage rests on the asymmetric-Vt, gate-length-biasing, and retentive-gating subset and this row is correspondingly at the weaker end for memory. Sub-threshold is declined for the active set (it would forfeit the SRAM speed the rows above credit) and kept only for idle-bank retention; the dynamic, data-dependent variants (workload-tracking body bias, activity-driven gating, adaptive assist) are declined as a data-dependent power channel (§15). A tier that picks a multi-port (8T/9T/10T) cell for stability or minimum voltage trades density, not speed. |
| Mem / security | Capability-checked DMA, no IOMMU/IOPMP (§15) | Added | **−0% to −3%** | DMA / I/O-heavy | Capability-bounds + tag check at the fabric; no page-table walk (lighter than an IOMMU); externally corroborated by CapChecker's measured ~1.4% for boundary capability-checking on heterogeneous accelerators (Cheng, Markettos et al., ISCA 2025). |
| Mem / security | Device-space stores non-bufferable: drain-then-issue, accept-before-retire (§15, R-15-015b) | Added | **≈0% general; −0% to −3%** | MSI / cross-core notification, MMIO-heavy device setup | A device store leaves the core only after the store buffer has drained and completes at the endpoint before retiring, so it pays a drain plus a fabric round-trip where a posted write would have paid neither. **Not optional and not bought for performance:** it is what keeps `fence.t`'s padded constant a function of the partition class rather than of the slowest endpoint the outgoing partition touched (R-15-218), and what keeps SRAM-store→device-store inside TSO (R-15-015). Cost is concentrated rather than diffuse: MMIO configuration is cold-path by construction (R-15-140) and doorbells are per-batch under R-11-010's ring-depth amortization, leaving the **MSI send** (interrupt-send being a store to an interrupt file, R-15-064, R-08-032) as the one class paying at rate, mitigated by the same batching-at-the-source the ring-window sizing already prescribes. The round-trip is bounded and static under TDM arbitration (R-15-225) and terminates in the endpoint's island-clock FIFO (R-15-196), so the typical accept is fabric-rate and enters §11 as a known constant rather than as variance; only a **full** FIFO degrades it to the link's own rate, which is the case R-11-010's depth sizing already governs. **The term is confined to the compartments that actually own a slow endpoint**, because device authority is provisioned by latency class (R-15-015c): a grant does not span a fabric-rate register block and a divided-clock endpoint, so the slow endpoint prices its own thin driver compartment's slot and nobody else's, and the split is taken only where that endpoint dominates the bound (R-15-015d). Partly self-funding: with R-15-015a's destination set extended to device endpoints it makes every device ordering edge structural, retiring the device consumer of `fence` and leaving only userspace store→load synchronization as a possible drain consumer. |
| Isolation | Non-work-conserving static cyclic scheduler (§7) | Added | **−10% to −30%** | mixed-load throughput | Idle slots stay idle; no slack donation (that would be a timing channel). **Range scores idle-slot waste at low discretionary population only.** **The worse end is scored with bound-directed lowering in place, which is what moves it from −35% to −30%:** a slot is billed at its WCET and not at what it uses, so half this row is the padding between the two, and R-18-014c makes emitting the tighter-bounded of two architecturally equivalent lowerings a conformance duty of both required compilers rather than an off-device optimization a build may skip. Its return is concentrated on **control-flow shape** (loop bounds that discharge syntactically instead of falling back to a declared maximum, bound-inflating control flow hoisted out of bounded regions, branch-free arms costing one figure rather than a worst one) and **not** on per-instruction timing, where an in-order, fixed-latency, cacheless core already has WCET ≈ ACET and nothing is left to recover. It is also worth nothing on the baseline, whose work-conserving scheduler bills elapsed time and to which a tighter worst case is invisible, so this is gap closed rather than a pass both machines run. **The better end does not move**, the structural half being unreachable by any lowering: an idle slot is burned whether or not its bound was tight. It does *not* cover the 1/n division of the discretionary band among live compartments, which dominates the waste term past a few compartments per core and is booked as a capacity wall (foreground fast, background near-stopped) in §17's population-wall entry rather than as a percentage here. |
| Mem / security | No hardware caches, flat SRAM hierarchy (§15) | Substituted | **−10% to −40%** | latency-bound / pointer-chasing scalar | L1/L2/LLC deleted: over flat SRAM there is no slow tier to cache, so latency-bound scalar code that hits a cache on the baseline pays main-SRAM latency here on an in-order core (pure pointer-chase can still exceed the range), bounded by SRAM's low latency (a small multiple, not the order-of-magnitude a cacheless *DRAM* design would pay). **The worse end is scored with static layout in place, which is what moves it from −50% to −40%:** the §10 code order and the §8 memory plan's locality objective (R-08-012a) are required of every conforming build rather than hoped for off-device, and on the one machine where they are the *only* placement mechanism their marginal return is correspondingly large: co-locating objects the typed structure reaches together and packing frequently-reached fields into whole tag granules removes array accesses outright, where on the baseline the same pass only nudges a hit rate the cache was already managing. What no compile-time plan reaches is the dynamically-shaped working set a cache captures by observing it, so the row **narrows and does not close**; ≈0 for streaming and the vector/matrix paths (explicit scratchpads). A deliberate perf-for-proof trade, deleting the dominant WCET term, the cache-timing side-channel class, the coherence protocol and directory, and the way-partition apparatus. |
| Isolation | SRAM bank/macro partitioning, no interleave (§15) | Added | **−5% to −15%** | bandwidth-bound per island | Bandwidth quantizes to assigned banks/macros, and the quantization itself is not recoverable: an island has the arrays the attested map gave it. What the worse end no longer carries is *serialization inside* that quantum, because R-08-012a's bank spreading distributes concurrently-live objects across the island's own banks so its cores and DMA endpoints contend on one array less often; the plan adds no bank and borrows none (R-08-012c), so this is utilization within the grant, not a larger grant. |
| Isolation | TDM NoC arbitration, no best-effort QoS (§15) | Added | **−5% to −15%** | communication-heavy | Deterministic but lower fabric utilization. |
| Isolation | `fence.t` flush + eager V/M zeroize at switch (§7, §15) | Added | **−2% to −4%** | context-switch-heavy | Cheaper than usual, no predictor/speculative state to flush (`cbo.zero` helps). The switch **zeroizes and does not save** (R-07-014a), which is what sets the range. State traffic per switch is **one write pass** over the vector RF, vector CSRs, and scratchpad, not the five a save-and-restore discipline costs (read RF + write SRAM, then read SRAM + write RF for the successor, plus the zeroize), and `cbo.zero` makes that pass a wide block-zero with no read. **The low end does not move and the high end does:** scalar cores carry no V/M state and pay the `fence.t` padded constant alone, which is the floor at −2% and is unaffected; the V-class with a large matrix scratchpad set the old −10% top end, and it is that end the ~5× cut in state traffic takes down. Both terms narrow again with the 64+1-bit capability format: the capability register file halves, so the zeroize pass over it halves (R-07-014a), and the store buffer's capability entries halve, which is the quantity `fence.t`'s padded constant is stated over (R-15-088, R-15-218). Neither moves the range's ends, both being small beside the V/M state traffic that sets them. |
| Isolation | Slot-spanning V/M state sink in-compartment (§7, R-07-014b) | Substituted | **≈0% to −2%** | long V/M computations that span slots | The kernel carries no V/M state across a switch, so a computation spanning slots sinks its own working state to its own memory. Roughly neutral against the baseline rather than a new tax: it replaces a kernel saving *the whole* vector file for *every* partition at *every* switch with a compartment writing *what is live* only where it actually spans a boundary, which is less work for the same task. The residual is compiler conservatism (a sink wider than the true live set), hence the small negative tail rather than a clean zero. Booked as a **§11 in-slot WCET term, not a partition-switch term** (R-11-027). |
| Isolation | No hardware cache coherence (§15) | Substituted | **−5% to −20%** | cross-island sharing | There are no caches, so no coherence protocol exists anywhere; cross-island sharing goes through shared-SRAM ring windows whose release/acquire edges are ordered by Ztso and preserved by the fabric, with no fence, instead of transparent hardware coherence; within-island unaffected. |
| Isolation | Multikernel, share-nothing per-core kernel, messages not shared state (§7) | Substituted | **−2% to −15% cross-core coordination; +0% to +15% kernel-lock-bound multicore** | cross-core coordination vs kernel-lock-bound multicore | Share-nothing replaces shared kernel state and locks with per-core replicas plus IPIs, user rings, and bounded-round agreement (§7, §8): it costs cross-core round-trips and a small per-core replication footprint, but removes all kernel lock contention and cacheline bouncing (the Barrelfish thesis, growing with core count, and the reason no lock-free CAS consumer exists, §7). Within-core paths unaffected. |

| **Gain, added** | Bitfield extract/insert, custom opcode space (§15, R-15-067a) | Added | **≈0% to +2% time; −3% to −8% code size** | generated wire-format codecs and MMIO accessors; fetch-bound | **The profile's second code-size addition, and the one whose carriage a measurement can still revoke** (R-15-067d). RISC-V has no general bitfield operation, so a multi-bit field read is a shift-and-mask pair and a field write is a mask-materialize, clear, shift, and merge sequence; `bfext`/`bfins` make each one instruction, 2:1 on the read and 4:1 to 6:1 on the write. **The size figure is derived from where the code comes from, not from the RISC-V literature**, which is the whole basis on which the amendment was admitted (R-15-067b): the bit-aligned wire formats (ASN.1 UPER RRC, IEI/TLV 5G-NAS, 802.11 MLME) are parsed **and emitted** by Narcissus from one format description, so the insert form has a first-class consumer here rather than an incidental one, and every MMIO register accessor on the machine is generated shift/mask code, which is the entire driver surface. It is coarse and unmeasured all the same: the delta lands where generated codec and accessor code is a material share of the image, and the range above assumes it is. **The time column is nearly empty on purpose.** The extract's pair is a fused short dependent-ALU chain already (fusion row above), so scoring it as IPC would double-count; what survives is the insert's dependent chain, which is longer than adjacent-pair fusion collapses, and it is **not** what admits the instruction and is not scored under the §15 gate. Booked on the other side of the ledger and not scored here: a review-gate rerun (R-18-034), two Sail clauses, and one selection rule per backend (R-18-014a). |

|---|---|---|
| General scalar / interactive / branchy (compilers, OS logic, business logic) | **−45% to −70%** | Runs at ~**30–55%** of a conventional core. ## Headline total

- **General-purpose scalar / interactive code: ≈ −55%, range −45% to −70%** vs a conventional out-of-order RISC-V application core.
  Ordinary software *feels like* it runs at roughly **a third to a bit over half** the speed of what you would otherwise buy: the deliberate, spec-wide price of deleting speculation, dynamic prediction, reactive clocking, and the cache hierarchy, and of paying the CHERI, partitioning, and static-scheduling taxes.
  The memory path contributes little to that figure, carrying ECC and bank partitioning but no cryptographic stage at all.
- **The workloads the machine is built for, vector graphics/DSP, crypto, and matrix/AI, run at parity-to-many-times the baseline** (roughly **+3× to +100×** over a scalar baseline, depending on class), because RVV, the systolic units, and table-free crypto more than repay the scalar overheads whenever the work vectorizes.
- **Blended "typical desktop/phone" experience:** dominated by the scalar/interactive figure for responsiveness (**−45% to −70%**), with the accelerated paths pulling media, crypto, radio/DSP, and AI inference back to parity-or-better.
  Net: a machine that is **materially slower for general use and faster for the parallel workloads it targets**, exactly the trade §1–§2 declare.

### Sensitivity to the baseline

If the reference core is instead taken to be a **plain in-order RV64GC core** (the common shipping RISC-V application profile, dynamic prediction, MMU, DVFS, C extension, non-CHERI, no vector) rather than an OoO part, then two of the largest losses (in-order vs OoO, and much of the turbo gap) **disappear or shrink**, while the no-MMU, bit-manip, and CFI/ASLR gains and the vector/crypto/matrix gains remain.
**What does *not* shrink is the memory side.** An RV64GC part has a cache hierarchy, unpartitioned banks, a conventional interconnect, and scalar `F`/`D`, so the no-cache row (−10% to −40%), the bank-partitioning and TDM-NoC rows (−5% to −15% each), and the no-scalar-float row (−2% to −15%) all apply against it **in full**, exactly as they do against the OoO baseline. Swapping baselines retires the *core* rows, not the memory and isolation rows, and after the in-order term is removed the no-cache row becomes the largest single loss that remains.
Against that baseline:

- **General scalar: ≈ −20% to −60%** (static prediction, the flat cacheless hierarchy, bank/NoC partitioning, CHERI, and no scalar `F`/`D`, minus the single-address-space, bit-manip, fusion, dictionary-encoding, and SRAM gains, and minus the same static-layout recovery, which applies against this baseline too but returns less against it, an RV64GC part having a cache that was already doing the placement).
  The range is wide because it is **set almost entirely by cache residency**: a workload whose working set the baseline's cache was already holding pays the no-cache row at close to its full −40%, while one that streams or fits in the island's banks pays near zero there and lands at the optimistic end.
- **Vector / crypto / matrix: unchanged, still large net positives**, and larger still because a plain RV64GC baseline has no vector unit to compare against.

So the design's general-purpose penalty is **"roughly half"** against a premium OoO core and **"a fifth to well over half, depending on cache residency"** against an ordinary in-order core, and in both cases it *wins* on the parallel and cryptographic workloads it was built to run.
The in-order baseline is a *narrower* penalty, not a small one: deleting the cache hierarchy costs the same against a modest core as against a premium one, and it is the term that survives the baseline swap.

A second baseline axis is **memory technology**.
Both reference baselines above use DRAM, so the SRAM main-memory row (the big table) scores as a gain; against a hypothetical conventional system that also used SRAM main memory that gain would vanish, being a memory-technology effect rather than one the security architecture confers.
What the security architecture actually contributes on the memory axis is the *deletion* of the refresh, RowHammer, and PRAC machinery (§15), which simplifies the design rather than costing performance.
SRAM's mirror cost on that axis is higher idle leakage (§15), an energy effect rather than a throughput one and so not scored as a compute-% above; it is paid down by the static, composition-time cell levers (the low-leakage row), whose only compute-axis footprint is the small active-access cost booked there, the dynamic and data-dependent leakage techniques being declined as a power side channel.
