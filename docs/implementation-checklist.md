# Golden-Model Implementation Plan and Checklist: Two Languages, One Machine

> Companion to [spec.md](spec.md).
> Execution state is tracked in §12, where each milestone is split into checkable tasks as it is entered; §0–§11 stay the authority on what each milestone means and why.
> This is the **bring-up realization** of §18: how to stand the whole verified stack up as a *fast, executable golden model* generated **directly from the two verification languages**, before any of the optimized/production workstreams exist.
> It is non-normative; §N references point at the specification.
> Where the spec describes the *hardened* artifact (CompCert-CHERI *robust preservation*, on-artifact constant-time verification, RTL ⊑ Sail, WCET certificates), this document describes the *reference* artifact that comes first and that everything else is later checked against.
> §10 describes two executors, the Sail-generated **golden emulator** and a **CHERI-QEMU fork** beside it; §12 carries the execution state, where the fork's two jobs are re-homed and its items are struck, so the reference is the one whole machine this plan builds and the RTL under Verilator is the second implementation the differential rig adjudicates against it.
> The plan's most important milestone is two: **M8a**, the full stack booting on the reference, and **M8b**, the **matching scalar RTL artifact** in hand and corpus-green in co-simulation (§11). They were one rendezvous over two chains and are now two gates over the same two chains.

## 0. The discipline: two languages, two golden models

The entire base system is written in exactly two languages, and each yields an executable reference by extraction, refinement, or generation rather than by hand-porting:

- **Hardware, Sail.**
  One Sail model of the machine (ISA + datapath + modeled devices), parameterized by core class (§15), whose **C backend generates the golden-model emulator**, the executable ISA reference.
  Beside it runs a second executor of the same frozen profile, the **CHERI-QEMU fork** of §10, **untrusted evidence-producing machinery** like the compilers and analyzers (main-spec §6): the iteration vehicle and the differential rig's second implementation, never the reference, every divergence adjudicated against the Sail model.
  The *same* source later feeds the RTL flow (net-new blocks authored in **Kôika/Kami**, imported cores given Sail-SV-plus-commercial-FEV evidence, SystemVerilog generated for synthesis, main-spec §15) and the proof tools (Sail → Coq, Isla, and the **one Iris-over-Sail program logic**, main-spec §13); none of that is on the bring-up path.
- **Software, Rocq/Coq (Gallina).**
  Every TCB and base-system component is written in Gallina from one source, then lowered two ways for two roles, and **the on-device lowering carries no garbage collector.**
  The main spec's storage rule, *"no managed runtime … the GC runtime is banned"* (§10), is the discipline for the *whole* base here: a tracing GC puts an unverified runtime in the TCB and its unbounded pauses break the WCET real-time path (§11).
  So `CertiCoq → Clight`, which emits a GC, is **host-side only**, never in a shipped image:
  - **Host-side functional oracle, CertiCoq → Wasm.**
    Each component runs on a stock Wasm engine (**standard Wasm, not CHERI-Wasm**) to iterate on OS *logic* before it is lowered at all; this leg's standing value is needing no toolchain, no image, and no machine model, whole-*machine* speed being the §10 fork's job.
    It tests logic and values and never capability *enforcement*, which is validated on the purecap-on-Sail path below, so no CHERI semantics are needed (Wasm is a system execution target nowhere in this design, §14).
    A GC is harmless here, riding the host engine, never shipped, never in the TCB, never touching a timing bound; where a component is too slow or the backend too immature, fall back to `Extraction` to OCaml for that component alone.
  - **On-device purecap artifact, GC-free, by the component's memory behavior.**
    The purecap machine code that boots on the Sail emulator is produced by whichever Coq-native GC-free route fits, each already inside the trust base, so no collector and no new prover enters the image:
    - **Refine the Gallina spec to CompCert-C (VST/Iris), through CHERI-CompCert**, for the kernel (§5), the M-mode firmware (§3), and the heap-churning storage layers (§6, §7). This is the spec's stated end-state (seL4's design via CompCert/SECOMP, §5); the GC-free C comes first and its refinement *proof* is deferred.
    - **GC-free extraction with region/arena allocation**, for the allocation-light, arena-shaped components (the static init tree §8; **not** the admission checker §9, which is TCB whose binary nothing re-checks): **MetaCoq → Rust with `bumpalo` arenas** onto the certifying Rust→RV64+CHERI compiler (§18), with **MCQC** the standing precedent that push-button GC-free extraction exists.
    - **Fiat/Bedrock correct-by-construction synthesis to imperative Clight**, where explicit-memory code is wanted directly; already the platform's method for wire parsers (Narcissus, §5) and field arithmetic (Fiat-Crypto, §4).
    - **Vélus (Lustre → Clight)**, for the §12 server *control planes*: a **Coq-verified** synchronous-dataflow compiler emitting CompCert Clight, statically allocated (**no GC by construction**), with WCET, determinism, and causality structural (§5, §12). Like Narcissus and Fiat-Crypto it is a Coq-verified DSL and **not a third trust language**; Lustre's meaning *and* its compilation are both Coq objects.

**The two golden models are validated independently first, then composed.**
The Sail-C emulator is exercised by assembly/ISA tests and the Gallina components host-side as Wasm; then the components are lowered **GC-free** to purecap RV64+CHERI and run *on* the emulated machine.
Day to day that composed system runs on the Sail-generated emulator, which is the reference as well: §10's second machine is struck, and S4 is the measurement that says one machine serves both roles.

**One toolchain contract, stated once for every Gallina component below.**
Unless an entry notes otherwise, each base-system component is written in **Gallina**, exercised host-side on the **CertiCoq → Wasm** oracle, lowered on-device **GC-free** by one of the four routes above, and compiled to purecap **RV64IMV+CHERI**, the *same* binary running on the emulator (§10), the RTL in co-simulation, and the FPGA (§11).
So each entry below gives only its **Toolchain** (the GC-free route, and why the component's allocation behavior fits it), its **Start-from**, and its **Plan**, showing Language or Compiler-target only where a component genuinely differs (the Sail cores of §1 and §2, the Lustre control plane of §8, the two-checker split of §9).
The Wasm oracle and the standing ban on the GC'd `CertiCoq → Clight` path are this section's rule, not repeated per component.

### The one prerequisite (built first): a functional CHERI-CompCert backend

Because the platform is **purecap-only** (§15) and this plan is **purecap end to end**, the one piece of compiler work that gates the whole stack is front-loaded *before* Emulation (§10) and FPGA (§11): a **functionally-correct CHERI-RISC-V backend for CompCert**, its memory model widened to capabilities and provenance.
It is not built from scratch. **SECOMP2CHERI** (Thibault, Azevedo de Amorim et al., PriSC 2023) already carries CompCert through every pass onto a CHERI-RISC-V capability machine in Coq/Rocq, and the capability-and-provenance C memory model it targets is itself mechanized (Zaliva et al., ASPLOS 2024), so the prerequisite is to **re-home that backend to the §15 purecap profile and complete it** rather than to devise either a backend or a semantics.
The *working* backend, **differential-tested against the Sail golden model**, comes first; its own Coq correctness proof and the §5 robust-preservation theorem are deferred hardening, and because SECOMP2CHERI is itself a secure-compilation backend, completing it later discharges that deferral rather than starting over.
The spec lists the backend as a hard prerequisite, *"nothing boots without it"* (§6), so **priority zero** is the spec-consistent placement.
Three things ride the same deliverable rather than becoming workstreams of their own.
**R-18-014a baseline target support**: latency-aware scheduling, RVV autovectorization and SLP, legal register-arm `Zicond` if-conversion and its capability arm, and fusion-pair emission and adjacency preservation.
**The primitive surface beside those lowerings** (R-05-023b), which gates earlier than any of them: the kernel names `vmclear`, `fence.t`, `cspecialrw`, and `csealentry` on its own switch and trap paths, no source expression denotes one and no lowering pattern reaches one, so a backend carrying every lowering and no primitive compiles no kernel at all.
And **R-18-014c's bound-directed lowering**, a choice rule inside the backend rather than a pass to build, gated on its input rather than on itself: the WCET cost-annotation pass is scope-cut for bring-up, so until it lands the rule runs against the emulator-measured table exactly as sound §11 admission does (R-18-025).
The deliverable is bounded below by the compiler rather than by the image, so the milestone also carries an **assembler, linker, and image composer for the frozen dialect**.
No stock binutils assembles a 64+1-bit purecap dialect (isa-profile §4.1), so LLVM's MC layer and `lld` are re-homed as the untrusted assembler and linker, and the composer emits the position-fixed image whose composition-time-absolute call and address forms the profile's code-size decisions quantify over (R-15-036l), reproducibly, reproducible build being part of the checkers' bootstrap-root story (§9).
Verified assembly, linking, and image construction are deferred like the backend's own proof, covered later by the §5 source-correspondence theorem through a named instrument (R-05-023a: decompilation into logic over the pinned Sail term, checked in the §13 logic); the *working* binary path ships inside M1, because nothing downstream links without it.
**No purecap CertiCoq GC is on this critical path**: the on-device lowering is GC-free, CertiCoq's collector is exercised host-side alone, and the arena route targeting Rust rides the certifying Rust→RV64+CHERI compiler that §18 already makes priority zero. The discipline *removes* a priority-zero deliverable rather than adding one.

### The profile-freeze measurement instrument

The profile's code-size choices depend on generated artifacts that do not exist before bring-up, so their common measurement instrument is built as part of this plan rather than tracked as an open import question.
It is one deliverable with two milestones:

1. **M0 defines the measurement contract with the profile.**
   Name and version the freeze corpus, its generated-source inputs, the composition recipe, the admitted region classes, and the acceptance threshold for every choice; define the emitter-provenance schema that labels operand classes before assembly; and establish one report format recording the realized dictionary, bytes, and Sail-model worst-case cycles.
   The corpus includes the composed base image, generated Narcissus UPER RRC and IEI/TLV codecs, generated MMIO accessors, and that image's generated prologues, epilogues, calls, and global-address materializations.
   The contract is authored as the [profile-freeze measurement contract](freeze-measurement-contract.md), the authority on every corpus member, recipe step, provenance stratum, region class, threshold, report column, and CI predicate; this section stays the authority on what the deliverable is and why it splits across two milestones.
2. **M1 builds and wires the instrument into the functional CHERI-CompCert backend.**
   Add an ELF/link-map/provenance analyzer under `tools/`, make the backend emit the operand-class and region-class sidecars it consumes, and take cycle deltas from §1's Sail timing table rather than host timing.
   Run the report in this fixed order: compose and merge first (R-15-036i); select and report the dictionary with hit rate stratified by operand class (R-15-036h, R-15-036k); measure outlining and tail merging as a bytes-and-worst-case-cycles pair per admitted region class (R-15-036o, R-15-036p); then PC-relative versus composition-time-absolute call and address forms (R-15-036l), `bfext`/`bfins` forms (R-15-067d), the one further code-size candidate the same act weighs (R-15-067e), the indexed load/store scale immediate (R-15-007g), and the emitted adjacency histogram the frozen fusion set is selected against (R-15-031a), whose admission is the §15 exploration's rather than the report's.
   The single-check multi-register save/restore is a **nil row**, struck ahead of the freeze (R-15-036n), so the report carries the strike with empty byte and cycle columns and a measured row against it is an amendment rather than a freeze.
   One choice is measured on cycles rather than bytes and takes a corpus of its own: `rcstep`'s carriage is decided by the decoder's worst-case cycles per frame over the conformance streams, against the slot and decode ceiling the media server is admitted at (R-15-067h, R-15-238c), reported in the same report with its byte columns empty.
   Publish the corpus manifest, tool version, thresholds, per-extension deltas, and realized choices with the freeze; CI rejects a report omitting a required corpus member, provenance stratum, region class, byte column, or worst-case-cycle column.

### Explicit scope cut (what this plan deliberately does **not** build yet)

Per the mandate to produce a fast golden model rather than the optimized variants, the following §5/§6/§18 workstreams are **out of scope for bring-up** and are named here only so their absence is honest:

- the CHERI-CompCert **secure-compilation criterion** (robust preservation, §5): the *functional* backend above **is** built and only the theorem is deferred, with **SECOMP2CHERI** its vehicle, so golden-model software is purecap but not yet proven to preserve compartment isolation against an adversarial linked context;
- binary-level **constant-time** verification (§5), crypto being a Gallina *functional* reference with no CT guarantee yet. The CryptOpt-style field-arithmetic translation-validation toolchain is absent for a different reason, being **deleted** in the spec rather than deferred, under §5's rule against a net-new verified artifact bought for speed alone;
- the **certifying Rust → RV64+CHERI** toolchain's *certificate* mode and the Tier-2 memory-safety certificate (§5, §13), so no contained-Rust userspace: base components the spec assigns to safe Rust are written in Gallina for the reference. Its *functional* lowering is still the target of the MetaCoq→Rust arena extraction above, and that backend is a spec-committed priority-zero item (§18) rather than a prerequisite this plan invents;
- **RTL ⊑ Sail** refinement (Kami/Kôika) and the **full VST(Iris) refinement proofs** for the kernel and storage stack (§5, §6, §7): the on-device code is written GC-free in the CompCert-C shape those proofs target, but its machine-checked *"artifact ⊑ Gallina spec"* proof is deferred, differential testing against the Wasm oracle and the Sail emulator standing in;
- the **WCET cost-annotation pass** (syntax-directed over the typed control-flow graph, folded into the certifying toolchain, no standalone estimator, main-spec §5/§11) and the **interval-arithmetic cyclic-executive schedulability check**; timing is measured on the emulator, not certified;

None of these is discarded; each is the *hardening* layer that later replaces a golden-model component in place.
The golden model is the oracle they are all checked against.

**One thing that might read as deferrable is not.** The second static latency class (§15, R-15-247) is **in bring-up scope**: M0.14 puts both classes into the model as two fixed constants and M0.16 puts the refresh and discharge sequencer beside them as §12 matter, both on the serial path ahead of the C-class freeze, and the roster is fit to two classes from that freeze forward rather than to one and re-fitted later. What *is* deferred is the qualification evidence R-15-247m requires (R4, R5) and the droop closure at composition capacity (M9a), and deferring those is the ordinary shape of a measurement that wants silicon. The class is not: a model frozen against one latency constant and re-parameterized afterwards would re-open the freeze rather than extend it.

## 1. The processor: the fusion SoC (Sail)

The "fusion processor with an on-die iGPU" is, in this architecture, a single die on which the GPU/accelerator role is **dissolved into ISA-visible cores in one Sail model** (§15): there is no fixed-function GPU.
The "iGPU" is the **V-class** long-vector cores (software rasterization, compositing, codecs, ISP) and the **M-class** matrix cores (GEMM/AI); both share the scalar front end and differ only in datapath (VLEN, matrix geometry).
One model, parameterized by class.

- **Language**, Sail.
- **Toolchain**, the Sail compiler's **C emulator backend** (`sail -c`) for the golden model; the OCaml backend for a quick interpreter; Sail → Coq and **Isla** (symbolic Sail) reserved for the proof/obligation side (deferred).
- **Start from**, `riscv/sail-riscv` (the official RISC-V golden model) merged with `CTSRD-CHERI/sail-cheri-riscv` (the CHERI-RISC-V capability model).
  These already give a booting RV64 + CHERI ISA emulator; the work is *curation and extension*, not greenfield.
- **Compiler target**, Sail-C emits portable C; compile with host `clang`/`gcc` to a native `x86-64`/`arm64` emulator binary.
  The *emulated* ISA is **RV64IMV + CHERI, purecap**, curated to the §15 profile.
- **Plan:**
  1. **Curate to the §15 profile.**
    The frozen profile is the root of the schedule and is enumerated once, in the [frozen instruction-set profile](isa-profile.md): base and ABI mode, the adopted extensions, the exclusions with their grounds, the CHERI feature set, the custom and fork-and-frozen units, and the CSR bank, every row citing the requirement that admits or excludes it.
    Curation is the mechanical act of making `sail-riscv` ⋈ `sail-cheri-riscv` agree with that table; restating the table here would be a second copy of it to keep true, and the profile is precisely what §18 gates the rest of the schedule on.
    One fact belongs here rather than there, being about the start-from and not the profile: `Zabha` needs no new modeling, already present in `sail-riscv` as extension-gated byte and halfword width cases inside the `Zaamo` AMO instruction file, so it arrives as a width case of a modeled operation rather than as a new mechanism.
    The work is overwhelmingly subtractive, which is the point: every removal is Sail surface that never has to be modeled, refined, or reasoned about again.
  2. **Adopt Ztso and static-only prediction as model properties** (§15): the memory model is RVTSO; there is no dynamic predictor state to model at all (deleting it is *less* Sail, not more).
     Curation proceeds under Ztso as specified; the store-buffer deletion, *sequential consistency by absence*, remains the DSE question [architectural-alternatives.md](architectural-alternatives.md) books, evaluated in the exploration below rather than closed by this step.
  3. **Parameterize by core class.**
     Add the RVV long-vector datapath (V-class, VLEN=4096) and a **fork-and-frozen matrix extension** (M-class, systolic GEMM geometry) as ISA-visible, capability-checked operations in the *same* model; capability checks land on scalar-issued vector/matrix memory ops (per-element for gather/scatter).
     Model the **FEC units** (LDPC/polar) and the optional Keccak unit as fixed-geometry, core-issued, capability-operand instructions, no DMA, no firmware.
  4. **Carry the memory interface as two static latency classes** (§15, R-15-247): two fixed timing constants against the existing interface, per-class density, retention interval, bank count, and latency constants in `platform_config` and the devicetree schema, and the refresh and discharge sequencer beside them as §12 matter, a fixed-function register slave with no instruction fetch. No new instruction, no new access type, and nothing added to the decode surface (M0.14, M0.16).
  5. **Add the timing annotations** the spec's §15 mandates name (fixed-latency DIV/FPU/AMO, mask-independent vector timing, static-fetch timing) as an annotated layer on the model, so the *same* Sail source is ready for later WCET/CT/Ztso obligations, but treat them as documentation in bring-up, checked by measurement.
  6. **Generate the emulator** and freeze it as the executable ISA reference.
     Every software image below runs on this.

### Choosing the frozen parameters: a proof-aware design-space exploration

The class parameters above (VLEN per class, matrix geometry) and the platform's other frozen microarchitectural knobs, core count per class, issue width and pipeline depth, the SRAM bank/macro/tier-to-island map, software-scratchpad sizes, the FEC decoders' realization geometry, and the TDM-NoC schedule, are not guessed (there are no hardware caches to size and no integrity-tree structure to size, main-spec §15).
They are chosen by a **design-space exploration (DSE)** run off-model, ahead of RTL and silicon, whose utility function is **multi-objective: performance, area, power, WCET, and, as a first-class term, *proof simplicity*** (main-spec §15).
Three knobs are constrained rather than free, and each is constrained differently. The **first class's vertical tier count** is bounded by R-15-163's conditional materials grading, a reading of the outside world rather than a point in the space, so the DSE ranges under whatever bound that grading returns. The **CBO block size** is welded to the tag group (R-15-007q) and must satisfy a first-class SRAM macro geometry and a second-class deck row and page geometry at once, so what M0.13 hands the search is a feasible interval and a value satisfying only one geometry is a search defect rather than a candidate. The **second class's bank count** carries the R-15-247g droop envelope as a **hard admission constraint rather than an objective**: infeasible points are pruned exactly as every candidate failing the five-part test is, and the two quantities it does trade against, the island bandwidth ceiling and the read energy per bit bitline capacitance sets, are objectives on the same knob (M0.17).

- **Proof simplicity is an explicit objective, not an afterthought.**
  A smaller, more regular microarchitecture is a smaller Sail model and a cheaper **RTL ⊑ Sail** refinement (the FPGA/silicon arrow of §11; deferred, main-spec §18, the least-built layer of the stack), so the DSE that improves performance can *reduce* the verification surface at the same time.
  The term is a proxy, estimated Sail-surface size, decode/state complexity, and per-candidate refinement effort, cheap to score inside the search loop.
- **The admission test is a hard constraint, not an objective.**
  Every candidate must clear the five-part admission test and the non-interference / schedulability obligations (main-spec §15, §8, §11) to enter the Pareto front; infeasible points are pruned, so the search ranges only over the proven-safe envelope.
  Its output is one frozen configuration that the per-class RTL ⊑ Sail proof then actually discharges, the proxy costs search quality, never soundness.
- **Tooling and staging.**
  An off-the-shelf multi-objective optimizer (NSGA-II-class) or an SMT/ILP feasibility oracle wrapping the admission predicate, over a parameterized cost model, **untrusted evidence-producing machinery, like the compilers and analyzers**: its output is re-modeled in Sail and re-checked, so it joins no trust base (§0, main-spec §6).
  Deferred like the other hardening (§11): bring-up runs on hand-chosen parameters, and the DSE is layered on once the Sail cost model and per-class RTL exist.
  It is the concrete home of the *"search over the instantiation, never the specification"* discipline.
- **Four questions the exploration answers by name, so none closes by default.**
  **First the store buffer.** [architectural-alternatives.md](architectural-alternatives.md) books *sequential consistency by absence* as a DSE question clearing four of five deletion gates and turning on one quantity, whether **ρ ≥ 1** (guaranteed per-hart memory-issue opportunities over that hart's static peak memory-op issue rate) is affordable on every class. Because an affirmative answer reaches back into the frozen profile's `fence` and memory-model rows, it is evaluated as early as its inputs exist, and taken that early it returns **unevaluable on every class**: the guaranteed side wants the slot share, frame length and per-hart injection width from the schedule R-11-017 emits, the island bank grant from R-15-228's map, and the write occupancy R-15-247m measures at qualification; the peak side wants the issue width R-15-108 selects and has not, and a per-cycle memory-issue width **that entry now owes and has not selected**. Closing that ownership gap moved the operand from unowned to unselected and moved the call not at all, which is worth separating because the two read alike in a report. The savings half is no readier: R-15-220 makes the `fence.t` padded constant *be* the drain, so the gain is that constant against the switch rate less the residual pipeline drain, and only the switch rate is a static schedule property, the constant being a function of buffer depth and memory bandwidth (R-15-218) whose magnitude R-17-041 books as unmeasured. Two consequences outlive the missing coefficients: ρ is indexed by core class **and memory class** together, the second sitting behind a slower write constant by design (R-15-247); and gain and cost land on different classes, the switch rate being at its floor exactly where R-15-114 pins a server to a core rather than a slot.
  **The disposition is confirmed open on operands, and the re-evaluation is triggered rather than remembered.** The question returns to the DSE at the act that selects issue width and per-cycle memory-issue width, which is R-15-108's and is the last operand the peak side is missing; the guaranteed side's three arrive with the schedule, the island map and qualification, none of which this decision waits on separately. Closing it instead was available and is refused: an argument that has not been run is not an argument that failed, and declining on an absence of operands is the one ground [the alternatives register](architectural-alternatives.md) does not accept for a deletion.
  **Second the product floor**, a precondition recorded rather than an output: the first release is a mobile device against R-18-004a's eight-member workload floor, priced in the per-class capacity, bandwidth, and area comparisons R-18-004b states, with R-15-109a binding both to this search as hard constraints that prune rather than price. R-18-004d fixes the demonstration set ahead of the search, so no member is chosen once the candidates are known. Two of the five comparisons reach the search directly, the area fit against core count and issue width on the fixed planar area R-15-108a weighs, and the two bandwidth floors against the per-class bank count; the costs stand where they were booked (R-15-162, R-15-163, R-18-004) and R-17-053b enumerates the forfeits.
  **Third the masked datapath's order and width**, a search rather than a precondition: R-05-004a names the secret path as a dedicated masked datapath of the parametric-order HPC lineage and R-05-070 refuses a secret-labeled operand to every R-15-055 vector-crypto instruction, so what is selected is the sharing order *d* and the datapath width, both owed by R-15-108. Order sets the randomness-expansion rate, rising with the order and with the masked nonlinear gates per cycle, landing in the crypto core's §11 slot budget through the R-15-241 DRBG; width sets the bulk symmetric ceiling per-extent AEAD (R-10-022) and link-layer encryption (R-12-039) are sized by. The expander scales with both terms, so they are searched together against area and power, every candidate carrying the R-17-058d ineffective-fault redundancy rather than being retrofitted with it, and R-17-058a's per-share-noise remainder worsening as the width narrows.
  **Fourth the per-class capacity split**, a stated target rather than a reading owed: R-18-004b fixes what each class is scored against, two per-class floors stated as payload with the ECC and tag planes above them, a bound on each class's declared exclusivity fraction (R-15-172), and the roster's resident bytes over R-15-247s's two lists as the demand side. It fixes the second class's bandwidth targets in the same act, one for the M-class island's grant and one aggregate, which is what R-15-247p's bank count is scored against, so M0.17's island bandwidth ceiling is an objective above the floor and a hard constraint below it. What the floor does not settle is the cycle-criticality reading: which regions are genuinely cycle-critical stays the memory plan's to place, and M1.9 is where it is read rather than assumed.

## 2. Root of Trust (Sail scalar RV64+CHERI core + Coq firmware)

The RoT is an on-die OpenTitan-class block with its own scalar RV64+CHERI control core, TRNG, OTP/key store, monotonic counters, and the watchdog (§9, §15), the platform's only management processor.
Its capability format is the main die's purecap format (§1) in a minimal scalar profile (no V/M, no C), so the one Sail model and the one CHERI-CompCert backend cover it, *not* CHERIoT's distinct compressed encoding.
Two advantages past that uniformity fix the choice: as the **root of the capability forest** the RoT mints and measures the very RV64 capabilities the main die executes under, which a 32-bit CHERIoT core could not even represent, so the boot handoff would otherwise cross a capability-format seam, and as the sole management processor its **64-bit reach** addresses the whole multi-GiB die directly, keeping measured boot clear of the 4 GiB windowing a 32-bit RoT would need in the measured path.
In the golden model it is a *second, smaller Sail core* plus a *Gallina firmware*.

- **Language**, Sail for the scalar RV64+CHERI control core and its peripherals (emulated by Sail-C on the host), Gallina for the firmware.
- **Toolchain**, GC-free CompCert-C through CHERI-CompCert; this small, mostly-static firmware has no heap, and it targets the **scalar** RV64+CHERI subset (no V/M) rather than the main-die RV64IMV.
- **Start from**, `lowRISC/opentitan` and the **Ibex** core as the functional/RTL reference, with **CHERIoT-Ibex** (the Sonata core) as the existence proof for CHERI on an Ibex-class core; the control core itself is the `sail-cheri-riscv` base configured to a minimal **scalar RV64IMC+CHERI → RV64IM+CHERI** profile (no C, no V/M) in the main die's purecap capability format (not CHERIoT's separate encoding).
  Model OTP, TRNG (as a seeded PRNG in emulation), monotonic counters, and the windowed watchdog as Sail memory-mapped devices.
- **Plan**, model the RoT as a minimal scalar RV64+CHERI Sail core with its peripherals; write the **measured-boot / seal-unseal / attestation-quote / anti-rollback-counter** logic in Gallina (functional reference; PQ signatures via the crypto core of §4 below).

## 4. Verified crypto core (Coq)

Boot verification, attestation, sealing, and the AEAD used by storage (§6 item 2, §10).
The spec's production form is verified C compiled through CHERI-CompCert **end to end, the field-arithmetic kernels included** (the CryptOpt route is deleted by §5's rule, not a later phase), with constant-time verified on the artifact, the secret-handling datapath **masked** with *d*-probing and composition theorems verified on the artifact against the probing-model statement (R-05-004a, R-15-053a), and SSProve/FCF reductions (§5); the **golden-model form is a Gallina functional reference** with no constant-time, masking, or reduction guarantee yet.

- **Toolchain**, GC-free **CompCert-C through CHERI-CompCert** (or GC-free extraction), the *same* route the hardened form uses for the field arithmetic, so no crypto component changes producer between the reference and the end-state; constant-time is **not** claimed in the golden model, on-artifact CT verification of the crypto core being the deferred end-state (§5).
- **Start from**, **Fiat-Crypto** (already Coq-native) for classical field arithmetic; for **ML-KEM / ML-DSA** and **SHA-2/3, AES-GCM / ChaCha20-Poly1305**, write Gallina functional specs (reference implementations), using the FIPS 203/204/205 vectors and `libcrux`/`HACL*` behavior as the oracle.
  No `F*`/Z3 dependency enters the golden model, these are *reference* implementations, correctness-by-testing now, reduction/CT proofs later.
- **Plan**, assemble a Gallina crypto module exposing hash, AEAD seal/open, ML-KEM encaps/decaps, ML-DSA sign/verify, and a DRBG seeded from the RoT TRNG.
  Validate against known-answer tests via the Wasm build.
  This module is a dependency of the RoT (§2), the object system (§6), and the filesystem (§7).
- **Masked end-state**, deferred with the other hardening rather than a golden-model property.
  The datapath is R-05-004a's **dedicated masked datapath** at parametric order *d* and not a masked instance of the vector crypto units, so the ensemble below runs over an object of the shape it is demonstrated on rather than over an eight-lane VLEN=4096 core.
  Start from the parametric-order HPC lineage (SMAesH, COMPRESS, and the OpenTitan first-order DOM AES/KMAC blocks with their stream-cipher randomness expansion), and run the tool ensemble (SILVER exact per gadget, PROLEAD statistical on the composed implementation, MATCHI compositional, and Coco-class execution-aware verification against the netlist, the R-15-053a discharge) as **untrusted evidence-producing machinery, like the compilers and analyzers**, VERICA/FIVER-class combined verification joining it for the R-17-058d ineffective-fault countermeasure, which is selected with the masking rather than after it.
  The load-bearing artifact is the Coq statement, and that half imports nothing: no proof-assistant masking development exists in Coq, so the probing model, a PINI-class composition theorem, and the R-17-058d reduction theorem are original formalization. Their nearest start-froms are three different answers rather than one, which is what a costing must not blend: the arithmetic half has a **Lean prime-field PINI development** to transcribe, machine-checked and in the wrong prover; the Boolean half the AES and Keccak datapaths need has the EasyCrypt gadget proofs and nothing nearer; and the reduction theorem has nothing machine-checked in any prover ([inspirations.md](inspirations.md), and §12's four post-M10 cells, which price the three separately).
  The module's DRBG carries the R-05-004a expansion role, its computational security a named assumption rather than a silence, and ML-DSA signs hedged on this path (R-05-004a).

## 5. Kernel (Coq)

A **bespoke minimal capability core**, seL4's endpoint and non-interference model as the design base (not a transcription of mainline seL4), instantiated once per core (multikernel, §7): endpoints + notifications, partition contexts, a static cyclic-executive schedule (no MCS), CHERI epoch-and-load-filter revocation over a kernel-owned grant table (§8), the CHERIoT-lineage switcher/sealing and interrupt sentries (§15), **single address space, no VSpace/page-table objects** (the MMU is deleted, §7/§15), and **no untyped memory, no capability space, and no derivation tree** (§7, §8).
The stripped design is what makes the greenfield Coq proof feasible: the deletions (VM, MCS, SMP, S/U modes, PMP/IOMMU) remove the proof-heaviest and least-maintained layers of `l4v`, and the object-model deletion removes the retype invariants, the capability-space lookup refinement, and the CDT revocation proof that were the largest blocks remaining after them, leaving the novel CHERI pieces no base supplies (the seL4/CertiKOS and object-model rationale in [inspirations.md](inspirations.md)).

- **Toolchain**, **GC-free CompCert-C refined against the Gallina spec through CHERI-CompCert**, the seL4/CertiKOS/VST method the spec mandates (CompCert/SECOMP, §5).
  seL4 does **zero post-boot allocation** (§7), so the running kernel needs neither a collector nor even a heap; extracting it through a GC would wrap an allocation-free design in a managed runtime, exactly backwards.
- **Start from**, seL4's **endpoint and non-interference design** as the design template, which M4.1a's provenance fork leaves as an idea and not as an artifact: no object of seL4's Haskell executable specification is translated into this tree, so the Gallina objects are authored from the design this repository already specifies and the platform keeps one licence, with the design's own statement and review standing where a tool-carried transcription's assurance would have stood.
  Reuse the seL4 ABI and object model for the **surviving object types only**, authoring without the VSpace/paging and MCS classes rather than transcribing then stripping them, and cross-check the CHERI single-address-space and temporal-safety realization against CheriOS's reservation/claim model and CHERIoT's revocation (§15). For bring-up only the *executable* Gallina model is needed, not yet the proof.
- **Plan:**
  1. Author the surviving object types (dropping the VSpace/page-table/frame-mapping classes, single-address-space, §7; the MCS scheduling-context classes, a static cyclic executive replaces them, §7/§11; and the untyped, retype, capability-space, and derivation-tree classes the object-model deletion removes, §7/§8), endpoint/notification IPC, the partition context, and the cyclic-executive schedule in Gallina as an executable state machine, with revocation stated against the CHERI epoch, grant-table, and load-filter model no seL4 design supplies.
     The one call that gated this authoring is taken: M4.1 drops the quiescent-point proposal, so revocation is written in the incremental preemptible form R-08-007 specifies.
  2. Exercise it host-side via the Wasm build (create/derive/revoke capabilities, IPC round-trips, slot-overrun faults), the fastest way to shake out the logic.
  3. Refine the Gallina spec to GC-free CompCert-C (**the C is authored against that specification**, taken at M4.1b: the CHERI-Alliance **CHERI-seL4 / CHERI-Microkit** release named here as the purecap C to start from is GPL-2.0-only at its kernel half, with the CHERI work contributed under that tag rather than beside it, so it cannot be composed with this repository's Apache-2.0 content and the maintained-code start-from is forfeit), compile through CHERI-CompCert, and boot **one instance per emulated core** with strictly disjoint state (the multikernel is the *sequential* kernel duplicated, §7), physical partitions enforced by **CHERI capability bounds**, each instance's partition-bounded root capability (§7), no PMP.
  4. Defer only the *proofs*: the functional-refinement proof (C ⊑ Gallina spec) and the non-interference theorem (§8), layered on later without changing the Gallina spec or the C; when they begin, the **purecap CHERI-C kernel refinement leads as the early kill-switch** (no CDT revocation proof stands in that role, there being no derivation tree; the object-model rationale is in [inspirations.md](inspirations.md)), leaving the refinement over CHERI-C semantics and the multikernel non-interference composition as the novel proofs that validate or falsify the route first.
     Purecap, GC-free compilation is **not** deferred, the §0 prerequisite backend means the kernel is purecap and managed-runtime-free from first boot.

## 9. Admission checkers (CHERI-TAL type-checker ⋈ Coq/MetaCoq proof kernel)

**Two checkers, stratified** (main-spec §5/§6/§13).
The **on-device admission checker** is a *CHERI typed-assembly-language type-checker*, order-10³ lines, decidable, the small on-device axiom that validates every installed binary's **typing derivation** (Tier-2 memory safety, CFI, no-codegen, ABI/type conformance) against the spec/Sail-model versions.
The **CIC proof kernel** (MetaCoq-lineage, honestly larger) validates every installed binary's artifact-local source-correspondence theorem, and validates the deep Tier-0/hyperproperty proofs (functional refinement, non-interference, crypto reduction, the *residual unstructured* constant-time and WCET, filesystem) predominantly at release time over the base-image TCB, the structured constant-time and WCET cases being type-level in the CHERI-TAL (main-spec §5).
Both are the component class whose *golden model is essentially its production form*.

- **Language**, Coq/Gallina both: the CIC kernel is a proof-term type-checker; the CHERI-TAL checker is a typed-assembly type-checker whose **soundness metatheorem** (well-typed ⇒ safe over the Sail model; foundational-TAL / RustBelt / WasmCert-Coq lineage) is proved once in Coq.
- **Toolchain**, **VST-refined CompCert-C through CHERI-CompCert**, the same verified-compilation route as the kernel (§5) and storage (§6/§7), for **both** checkers: they are TCB, so unlike the contained components they may **not** ride the unverified MetaCoq→Rust extraction backend and the untrusted Rust→CHERI userspace toolchain (§0), that route is admissible only where the emitted binary is itself re-checked, and nothing re-checks the checkers.
  Arena/region allocation stays the memory discipline (type-check one proof term in a bump arena, then wipe it whole), but expressed as the explicit-memory CompCert-C the VST refinement covers, not GC'd, not unverified-extracted.
  **CertiCoq is *not* used on-device either**, its verified extraction still emitting a GC, an unverified runtime inside the one axiomatic component (§0).
  The published **CertiCoq → Clight → CompCert** pipeline (MetaRocq's checker extracted through CertiCoq, with **VeriFFI** the verified Coq↔C boundary and **CertiGC** the verified collector) *is* a real assemble-not-build route to a verified CIC checker, and it is **declined for the on-device component deliberately**: even a verified GC is a runtime carve-out inside the one component whose binary nothing re-checks, and *engineering is free while trust is scarce* (*verify rather than hedge*, main-spec §15).
  It is retained host-side and stands as the documented fallback should the VST refinement of the full CIC kernel prove intractable; VeriFFI is then the wiring proof for *that* fallback and not for the on-device checker, which is refined to C and so has no Coq↔C boundary to prove.
- **Start from**, for the **CIC kernel**, **MetaCoq**'s verified checker (the "MetaCoq-style self-verification target" of §6), a Coq-implemented type-checker for Coq terms, as the Gallina *specification* the on-device C kernel is refined against (VST), inheriting MetaCoq's in-Coq soundness rather than re-deriving it through unverified tooling.
  For the **CHERI-TAL type-checker**, the foundational-TAL / RustBelt / WasmCert-Coq type-soundness lineage, its type system the CHERI-RISC-V instantiation carrying the temporal-safety + typed-control-flow residual CHERI leaves (main-spec §5/§18), the language it instantiates being specified separately in [typed-assembly-language.md](typed-assembly-language.md).
  The capability-machine program logic the soundness metatheorem builds on is already mechanized in Coq/Iris, **Cerise** (the universal contract for a capability machine, §13), its attestation extension **Cerisier**, and **StkTokens** (linear/affine stack capabilities), with **Katamaran** (semi-automatic separation-logic contracts over its μSail embedding of an ISA, a translation from the pinned Sail model that R-13-016 books as owed) available to discharge the per-instruction obligations, so the metatheorem extends a mechanized foundation rather than starting from scratch.
- **Plan**, refine both checkers to CompCert-C (the CIC kernel against the MetaCoq Gallina spec; the CHERI-TAL type-checker against its soundness metatheorem) and compile through CHERI-CompCert as the admission oracle; each package carries the exact hash-named source closure plus a correspondence proof through assembly, linking, and image construction, while in bring-up the packages they check are the golden-model components themselves (proof objects and typing derivations are thin/stubbed until the Tier-0/1/2 proofs exist).
  Their role hardens *in place* as real proofs arrive, the checkers do not change, only the derivations and proofs they are handed.
  **The checkers' own binaries are the bootstrap root** (§6 item 6 of the main spec): no package certificate can cover the admitters, so their trust rests on reproducible build + DDC + the RoT measuring them into the measured-boot chain, not on any admission proof of themselves.

## 10. Emulating the hardware: the golden emulator and the fast emulator

The hardware golden model *is* the Sail-C emulator of §1; "emulating the hardware" is standing up two whole machines around the same frozen profile, the golden one generated from Sail and the fast one forked from CHERI-QEMU, and booting the GC-free purecap software (§0) on both.

- **Single-core ISA emulator (day one).**
  `sail -c` on the curated model (§1) gives a fast single-core RV64IMV+CHERI emulator.
  Drive it with hand-written and randomly-generated ISA tests; this validates the *hardware* reference independently of any software.
- **Whole-machine harness.**
  Wrap the Sail-generated core with a thin host-C system harness that provides: **multiple core instances** (C-class ×N, V-class, M-class, the S-class sentinel, and the RoT RV64 core of §2), **physical memory** with the modeled ECC behavior as no-ops-with-latency (there is no memory cryptography to model, §15), and the **modeled devices**: a UART console (modeled first, nothing is debuggable before output exists), the block device the storage stack (§7) mounts, capability-checked DMA (default-deny capability-bounds checks on device transfers), the register-slave transceiver stream (with its fixed-function link-layer timing sequencer, §15), the scanout DMA block, and the RoT peripherals.
  Devices are modeled either as Sail memory-mapped regions (preferred, keeps them in the one language) or as C shims in the harness where that is faster to iterate.
  The **NoC and islands** are modeled as a simple address-routing layer in bring-up (the TDM schedule and non-interference semantics are §15 hardening, not needed for functional emulation).
- **Composed full-system golden model.**
  Boot the stack in the spec's §9 order on the harness: RoT core + firmware (§2) → M-mode firmware (§3) → one kernel instance per core (§5) → init (§8) → object system/transactor (§6), filesystem (§7), crypto core (§4), checker (§9), every image **GC-free purecap RV64IMV+CHERI**, produced by the §0 on-device routes (CompCert-C/VST through CHERI-CompCert, or arena extraction through the Rust→CHERI compiler), *never* the GC'd `CertiCoq → Clight` path.
  This is the reference machine: purecap, managed-runtime-free software on the verified-by-generation ISA.
- **The fast whole-machine emulator: a CHERI-QEMU fork (the daily driver).**
  A Sail-generated interpreter is faithful, not fast; the machine the stack is *developed on* is a **fork of CHERI-QEMU** curated to the same frozen profile, which buys TCG JIT speed, a GDB stub, deterministic `icount` execution, snapshots and record-replay, and mature machine/device scaffolding on day one.
  It is **untrusted evidence-producing machinery** (§0, main-spec §6), like the compilers and analyzers: it joins no trust base, is never the reference, and every divergence is adjudicated against the Sail golden model, so the only possible outcomes are a fixed fork or a genuine spec-versus-intent finding, the error class no proof covers (R-17-016).
  The fork is a re-parameterization rather than a checkout, because the dialect is bespoke (R-15-007): stock CHERI-QEMU implements the ISAv8/v9 128-bit lineage, so the work is narrowing its `cheri-compressed-cap` library to the §4.1 fields, a fresh parameterization rather than a selection among the instantiations it carries; implementing the frozen decode surface; deleting the MMU path (`satp` Bare, no S/U modes); adding the VLEN=4096 RVV datapath and the matrix/FEC units with per-element capability checks; and defining one machine type modelling exactly the harness's device list, no virtio, no PCI, no stock `virt` zoo.
  RVTSO is honored by construction: deterministic round-robin `icount` execution is sequentially consistent, so every behavior it exhibits is TSO-legal, and the weak outcomes an SC executor cannot exhibit belong to Isla's litmus exploration rather than to this vehicle.
  This is the instrument R-17-048a prices: the bespoke dialect degrades the stock oracles (Spike, QEMU, the CHERI test suites), and the fork is the compensating purchase, a second implementation of the profile from an independent code lineage, so spec-versus-intent divergence always has two executors to disagree.
  The plan's **intermediate goal** is the full §9-order boot on this fork; the composed Sail emulator re-runs the same boot in CI as the golden cross-check.
  **Its execution state is §12's and the fork is not built there**, which is this document's standing division rather than a contradiction: this section stays the authority on what the vehicle is and why it would be wanted, and §12 records that its second-executor job is re-homed onto the RTL under one trace format and its daily-driver job is measured before it is bought. The two rulings that buy it are named there.
- **Three loops, one source.**
  For OS-logic iteration that needs no ISA in the loop at all, run the *same* Gallina components as **CertiCoq → Wasm** on a host Wasm engine: the inner loop, no toolchain, image, or machine model required.
  The QEMU fork is the middle loop, the whole machine at JIT speed; the Sail-C emulator is the outer loop, the reference every divergence returns to.
  All three execute artifacts of one source, so a bug found in any loop is fixed once.
- **Test generation and differential testing: one corpus, one trace format, three executors.**
  Use **Isla** (symbolic execution over the Sail model) to derive ISA test vectors and the concurrency/Ztso litmus set from the frozen model, normalizing every legal `fence` encoding to the profile's two outcomes (`drain | nop`) rather than generating predecessor/successor-set cases.
  The rig is a named deliverable rather than a habit: the corpus is versioned at M0, and its executions are compared through one **capability-widened RVFI-style commit trace** (PC, instruction, register and memory effects, plus tag, bounds, permissions, and seal state) emitted by the Sail emulator, the QEMU fork, and the RTL (via its `rvfi` port, §11; R-15-094 already names `rvfi` the cheapest bring-up evidence).
  Both are the [differential corpus and commit-trace schema](differential-corpus.md), which is the authority on the corpus's membership, on how a member is written, and on what each record of the schema means; this section stays the authority on what the rig is for and which executors it adjudicates.
  One CI runner diffs the trace per-instruction over the corpus, and per-boot (console, event, and final-state digests) over the composed images where instruction lockstep is too slow.
  The Sail emulator stays the **oracle** for everything downstream; the QEMU fork and the FPGA are both checked against it, never against each other alone.
- **Staging.**
  C-class scalar emulator + software rendering first; add the V-class vector datapath, then M-class matrix, then FEC, then multi-core + islands, mirroring §18, each class extending the *same* Sail model and re-generating the emulator.
  Each class lands in the Sail model first, then in the fork, then in RTL (§11's ordering rule), so every executor is brought up against an already-validated predecessor.

## 11. Building an FPGA from it all

The golden model is Sail, not RTL, so an FPGA needs RTL.
Per the two-language ideal and the semantic-anchor budget (main-spec §5), RTL ⊑ Sail is discharged along a **three-route ladder** (main-spec §15), detailed just below: net-new blocks **authored in a formal-semantics HDL** and proven against the Sail source, imported cores given **Sail-SV + commercial-FEV** observational-equivalence evidence, and open cores kept as **differentially-tested functional references** for the early milestone, with the closing Coq refinement layered on afterward (§18).

- **Three routes to RTL, laddered by what each buys.**
  - **(a) Author the net-new blocks in Kôika/Kami** (Coq hardware DSLs): the blocks with no legacy RTL to preserve (the capability/tag-carrying DMA fabric, TDM NoC, and fixed-function sequencers) are written in the formal-semantics HDL and proven to refine the Sail golden model, with **PipelineGen** and **Sail → Kôika/Kami** generation as scaffolding rather than the design of record.
    This is the closing path and keeps the hardware on the single prover; **Erbsen et al.** (PLDI 2021, Bedrock2 + Kami) is the existence proof that an end-to-end software ⋈ hardware theorem rides exactly this spine, with no SystemVerilog in the trusted path (SystemVerilog is generated output for synthesis).
    A second spine for the same arrow is worth naming and is not a substitute: the **interaction-tree** line carries a Rocq semantics of RISC-V as an ITree and reaches both ways off it by bisimulation and refinement, proving a compiler-IR-to-RISC-V equivalence on one side and validating a **Kôika** ALU against the R-type integer operations on the other. It supplies a shared semantics and three case studies rather than an end-to-end theorem, and its hardware side is Kôika, so it moves neither the licence preference below nor the closing proof, which is still authored here.
    **Of the two, Kami is the default, and the ground is license rather than capability.** Kami is `MIT`; Kôika is LGPL-2.1 and its repository does not disambiguate `LGPL-2.1-only` from `LGPL-2.1-or-later`, carrying the bare licence text with no per-file election, which bears directly on onward compatibility. Authoring a block means writing Coq modules that import the chosen library, the configuration in which an LGPL library's reciprocity is least settled, and this route is the one place on the plan where such a term could attach to *authored design* rather than to a contained instrument. **Kôika is elected per block and the election test is written here rather than left to the moment**, because a test authored beside the block it admits is a test authored by the block. An election states three things and is refused without them: the property Kami cannot supply, named as a property of the block rather than as a preference; the term accepted, which on today's reading is LGPL-2.1 with the only-versus-or-later question undecided at the file, so an election accepts the stricter reading; and the containment, an elected block being authored so that what imports the library is separable from what does not. Absent all three the block is Kami's. Nothing is owed before this route opens, well after the co-simulation gate, which is why the preference and its test are cheap to record now and expensive to discover later.
  - **(b) Give the imported cores Sail-SV + commercial-FEV evidence**: Sail's SystemVerilog backend emits a reference model from the ISA and a commercial FEV tool (Jasper-class) proves the imported CHERI-CVA6 (and Ara/Gemmini) RTL observationally equivalent to it, the published CHERIoT-Ibex conformance methodology at application-class scale, unbounded observational-correctness evidence at near-zero method-development cost though the FEV tool is trusted (main-spec §6/§15).
    Their Coq close is deferred: author-in-Kôika where a block is being rebuilt anyway, or a proof over the shipped SystemVerilog if a foundational Verilog-semantics account matures.
  - **(c) Bring up open cores as functional references + differential-test**, take the open RTL substrate per class and validate it against the Sail emulator (§10) as the oracle for the *early* FPGA milestone.
    This is the pragmatic near-term path and matches the "fast golden model, defer the proofs" mandate: no RTL ⊑ Sail *proof* is required for the FPGA milestone, only differential agreement with the golden model, and the open cores are the differential-test reference substrate on which route (b)'s stronger FEV evidence is layered, while route (a) supplies the authored, proven net-new blocks.
- **Open RTL substrate (route b), per class (§18).**
  For the **C-class scalar** front end an *existing CHERI RV64 soft core*, **CHERI-CVA6** (Bristol / lowRISC / OpenHW) or the Bluespec **CHERI-Flute / Piccolo / Toooba** (CTSRD), *modified to static-only prediction* and a TSO store buffer per §15; **Ara** (PULP) for the V-class vector unit; **Gemmini** (Berkeley, Chisel) for the M-class matrix unit; open **LDPC/polar** cores for FEC; and for the **RoT**, **Ibex** + `lowRISC/opentitan` as the functional reference and **CHERIoT-Ibex** (Sonata) as the CHERI-on-Ibex reference, the on-die core itself a small **scalar RV64+CHERI** purecap core in the main die's capability format (§1), not CHERIoT's separate encoding.
  All are SystemVerilog/Chisel, synthesizable today.
  The **CHERI-CVA6** option specifically has a commercial-quality, formally-verified open track: the lowRISC / Capabilities Limited **COSMIC** project (2025–28) hardens it on OpenTitan IP and proves its instruction execution conforms to its ISA spec, the application-class successor to the CHERIoT-Ibex conformance proof, directly de-risking the *"RV64 application-class CHERI exists only as soft cores"* binding constraint (§18) and handing the RTL ⊑ Sail bring-up gate a real application-class artifact (see [inspirations.md](inspirations.md)).
- **Concrete bring-up artifact, CHERI Mocha (COSMIC's MVP-2 platform, `lowRISC/mocha` pinned at `v0.1.1`).**
  That COSMIC track ships a tagged, FPGA-synthesizable **secure-enclave SoC**, the CVA6-CHERI application core plus OpenTitan peripherals, booting to a terminal prompt on a **Genesys 2 (Kintex-7)** board.
  The edition is read from the tags rather than from the prose beside them: `v0.0.1` is MVP-1, bare-metal testing in CHERI and integer modes; `v0.1.0` is MVP-2, all blocks integrated with CHERI-Linux booting; `v0.1.1` is the minor release above MVP-2 that this row pins, carrying an FPGA reset fix and no change to the block set; and the default branch head stands above it untagged. RC-1, the sign-off release the README's timeline schedules for December 2026, is not cut. lowRISC's own announcement page still names the initial release and the README's release table marks `0.0.1` alone as available, the ordinary lag of a roadmap behind a tag.
  It is a **Start-from** for C-class-scalar-plus-RoT bring-up: the application core is the C-class front end, the bundled **entropy source, KMAC, ROM controller, SPI host, and mailbox** are functional-reference RTL for the RoT and its measured-boot chain, the **KMAC** doubling as a reference for the SHAKE-heavy PQ crypto core, and the bare-metal **HAL** (`sw/device/lib/hal`) is a Start-from for the verified DMA/MMIO/descriptor HAL.
  Its **AXI tag controller** is the functional reference for the one interconnect piece the purecap design most needs and the spec already owes (§17), the **capability- and tag-carrying fabric**: one CHERI tag bit per 128-bit region on the bus user bits, tags in a separate memory block from the data. This platform's granule is 64 bits (R-15-203), so it is a shape to follow rather than a parameterization to copy, and that separate block is the validity plane's own shape, the only tag plane the design carries (Write-before-Read is a type attribute rather than a second plane, §5).
  Its **OTP-backed rollback counter** port is likewise a reference for the anti-rollback monotonic floor (main-spec §9), while its **memory-encryption-key** ports are left unused: the memory path carries no key material, no cipher, and no integrity construction (§15), which is the single largest reduction in net-new Kôika RTL on the whole plan.
  It stays a *reference* and not an admitted artifact, under the same route-(b) disposition as every core above: its verification today is OpenTitan-style staged sign-off, UVM simulation plus bounded FPV assertions and three-reviewer checklists, with first sign-offs targeted at RC-1 (Dec 2026), which is not the unbounded **RTL ⊑ ISA conformance proof** the golden model wants (§18).
  Two pieces are pointedly *not* imported.
  The **debug module** is a development-visibility backdoor, admissible only where §15 already puts external debug: **gated behind RoT lifecycle state**, fused-off in production, never a shipping surface; its trace is the sole development cycle-measurement path after `Zicntr`/`Zihpm` are deleted.
  And Mocha's headline **CHERI-Linux boot** is the enclave-beside-Linux framing the design refuses (§14, *no Linux-personality shim*). The divergence is architectural rather than merely the software stack: Mocha fields an application-class core **precisely to give enclave OSes an MMU**, whereas this profile **deletes the MMU** outright (single-address-space, `satp` Bare, §15). So the CVA6-CHERI *datapath* transfers, the MMU-on configuration that is Mocha's whole reason for an application-class core is curated away, and Mocha's conformance evidence for that path covers hardware the platform never runs.
- **CHERI runs on FPGA, and purecap software is ready for it, no stop-gap.**
  CHERI *runs on FPGA today*: the scalar CHERI RV64 soft cores above make the **C-class FPGA purecap from the start**, and because the **functional CHERI-CompCert backend is a prerequisite** (§0), the purecap golden-model images boot on it directly, purecap from first bring-up, with no capability-degraded interim.
  The genuinely new RTL + Sail work (§18) is CHERI for the **V-class and M-class**, Ara and Gemmini are not capability-aware, so extending their vector/matrix memory ops to per-element capability checks is the real hardware effort, *not* the scalar core.
  The RTL is net-new and the *design* under it is not, which is worth separating before the effort is read as covering both: the **CHERI-RVV** line studied this exact join and settled that capabilities serve as memory references in every vector instruction, that bounds checks for elements inside a known range collapse to a single amortized check, and that legacy vector code compiles to purecap form unchanged. It is a proposal rather than an implementation, stated over the ISAv8 lineage rather than the frozen dialect and touching neither core above, so the design transfers and none of the hardware does. The amortization is the part that reaches past the RTL: an amortized check and a per-element one are different quantities, so it is the boundary R-15-085a's vector-memory rows would take a magnitude from if R-17-041's ever acquire one.
  The only *silicon* gate (§18) is fabricating a CHERI **ASIC** for a shippable product, irrelevant to emulation and FPGA.
- **Profile curation in RTL.**
  Two documents decide this and neither is restated here: the [frozen instruction-set profile](isa-profile.md) says what the hardware must implement, and the [microarchitectural absence contract](absence-contract.md) says what it must not contain and what evidence an auditor searches the elaborated netlist for.
  The second runs *during* FPGA bring-up rather than waiting on it: the imported cores exist today, so the contract's state enumeration and its synthesis-configuration provenance are recorded at the moment a core is first elaborated, which is also the moment the disabling parameters are chosen.
  Each row of either document is *less* hardware than the stock core, not more.
  One item is a re-parameterization rather than a removal, and it paces the scalar milestone: the imported cores implement the ISAv8/v9 128-bit capability lineage while the frozen dialect is 64+1-bit (isa-profile §4.1), so the CVA6-CHERI datapath's capability format is **re-parameterized, not configured**.
  The bespoke format is thus implemented three times across the plan, Sail first (the definition), the QEMU fork second (the fast oracle), RTL last (the implementation), landed in that order so each implementation is brought up against an already-validated predecessor.
- **Co-simulation is the RTL gate; the board is not.**
  The deliverable the MVP names (§12, M8b) is an **RTL artifact of record**: a versioned, lint-clean, elaborated SoC top, the curated C-class scalar core, the RoT core and its peripherals, the tag-carrying interconnect, boot ROM, UART, and block device, generated SystemVerilog where authored and curated SystemVerilog where imported, published with its synthesis-configuration provenance and absence-contract evidence recorded at first elaboration (above).
  It is *matching* when, under **Verilator co-simulation**, its capability-widened `rvfi` commit trace (§10) agrees with the golden model across the shared corpus, CVA6's existing `rvfi`/tracer port being the hook, and the composed purecap image boots to the same console and event digests as the golden emulator.
  Every clause in that sentence runs in CI with no hardware attached, so *a solid RTL file in hand* is a software-visible, reproducible claim; FPGA synthesis afterward validates timing closure and resource fit, not function.
  **The memory interface in that artifact carries two static latency classes** (§15, R-15-247), so co-simulation exercises both constants and the bank-staggered maintenance schedule: a bulk-resident access returns at the second constant, and a mode transition runs the discharge and refresh sequencer as §12 matter, with the fail-stop completion indication read once after its fixed dwell. What the FPGA cannot supply is the medium: the board has no oxide deck, so the second class is modeled at its constants rather than realized, and every figure behind those constants stays R-15-247m's to measure on a repaired macro (R4, R5). The co-simulation gate therefore proves the interface and the sequencing, never the device.
- **Synthesis + bring-up staging.**
  Synthesis follows the co-simulation gate: the artifact that boots in Verilator is the one synthesized.
  Target a large FPGA (Xilinx/AMD UltraScale+ or Versal class, or an open board where capacity allows).
  Bring up **C-class scalar first** (boots the same M-mode firmware → kernel → init stack from §10), then **V → M → FEC → NoC → islands**, class by class, each differentially tested against the Sail golden model.
  The **S-class sentinel** and RoT are small and come early.
- **Deferred hardening (named, not built here).**
The **riscv-formal/rvfi** BMC bring-up gate (on the generated SystemVerilog), the **Sail-SV + commercial-FEV** observational-equivalence evidence for the imported cores (route b), the **Isla**-generated obligations, and the closing **Kami/Kôika** RTL ⊑ Sail refinement over the **authored** net-new blocks (route a; §15, §18) are the path from "the reference cores differentially agree with the golden model" to "the shipped RTL is proven to refine it."
  They are explicitly out of scope for the FPGA milestone and layered on afterward, the golden model remaining the reference they target.

## 12. Build order, milestones, and execution state

Bottom-up, each milestone runnable against the prior one; the software track (M-numbers) and the RTL track (R-numbers) proceed in parallel after M0 and each closes at its own gate, **M8a** and **M8b**, rather than rendezvousing at one. The S-numbers ahead of both are the decisions neither track can take for itself and the instruments both run on. The Q-numbers beside them are the actions [the critique's product assessment](critique.md#the-two-theses) puts to the program, review actions that gate no milestone and close by a measurement or by taking an arm.

The order records a sequencing decision rather than an accident: realization is **scalar-first**, the V/M/FEC datapaths arriving last (M10), and the staging discipline of *add a unit only after a measured need* applies to the units alone, never to the capability width. R-15-007d freezes the width with the profile at M0, permanently, every capability in the immutable image and every sealed blob stored in the frozen format, so no later measurement can reopen it without invalidating stored authority wholesale; the width is decided once, at the freeze, and only the units are staged.

The milestones are also the review gate's clock: a crown-jewel row a milestone flips to `authored` enters R-05-150's independent specification review at the flip, not in a release-time batch, so each specification is read at the edition the proofs will be stated against rather than re-read from a corpus that has moved on.

**An upstream's license is read at the milestone that would incorporate it, never at release.** A license is a property of the *arrival* rather than of the shipped image, and it is the one property whose discovery cannot be repaired downstream: work built on an upstream whose terms forbid the composition is discarded rather than re-licensed. Two rules follow and both bite before a line is written. **A vendored tree binds this repository and a pinned submodule does not**, so pinning to read is free and vendoring is a commitment; [THIRD-PARTY.md](../THIRD-PARTY.md) is the standing account of which each upstream currently is. And **terms are read from the upstream's own licence file rather than inferred from its lineage**: taking an idea from a system carries nothing, and translating that system's artifacts carries whatever those artifacts carry. Every milestone below that would move an upstream from pinned to incorporated names its terms in its own entry. Four upstreams here are not permissive and they do not resolve alike: three carry a decision item ahead of the work, M1.1a for the compiler, M6.0a for the control-plane compiler, and M4.1a for the kernel specification, the one whose artifact would reach the shipped image; the fourth carries a containment rule at M2.1, the emulator fork being a development instrument no image links against. [COPYRIGHT.md](../COPYRIGHT.md) holds the licences this repository's own content is offered under, which is what the gates exist to keep available.

Five crown-jewel rows sit off this clock. The pinned Wasm guest semantics (inventory row 25, R-14-013b) gates no M-milestone, the platform interpreter it serves shipping with the §18-deferred application program rather than the base system; it is the inventory's cheapest retirement, a version-pin of the mechanized WasmCert lineage whose soundness and confinement theorems arrive with the artifact, so the cost is the pin, the subset cut, and the review rather than a formalization. The M1 CertiCoq → Wasm host-side oracle is unrelated to it, being build-farm machinery on the host that leaves R-05-085's device claim untouched.

**Those five are not the whole of what sits off this clock, and the rest is a gap rather than a schedule.** Ten further inventory rows read `not authored` and no item below authors one: the security policy model (row 2), the NoC and island isolation model (8), the bank-to-island binding map (9), the wire-format inventory and its Narcissus descriptors (10), the OPP and mode schedule statements (11), the reset and power sequence table (12), the calibration-manifest schema (13), the timing-annotated model's latency magnitudes (15), the verified HAL's hardware contracts (18), and the protected-sequence fault model (24). Where the plan names an owning entry at all it names it as a constraint some other item is read against, and [the inventory](crown-jewels.md) makes these milestones the retirement mechanism for that column, so a row with no item here is a row nothing retires. **Row 24 is the one already stated from the other side**, the post-M10 reduction saying outright that it stands over two objects this plan does not cost. **The load-bearing one is row 2**: it needs no toolchain, no image and no machine model, so it is `Wasm-parallel` by this document's own definition and openable today; [ApexTheorem.v](../proofs/ApexTheorem.v) is already parameterized on it, and CJ-SECOMP and the B-07/P-1 coverage cell both rest on it. **Reported and not closed**: opening cells for these is a pricing act and a register reading, not a currency repair, and inventing an estimate for one would be worse than recording that none exists.

**R-15-108's design-space exploration is deferred in §1's prose and has no cell either**, which is the same shape one milestone down. Sites across this document wait on its outputs and say so, at M0.8a's `frozen` flag, M0.8c's scratchpad size, M0.13's six owed rows, M0.15's comparison arm, M0.17's six pending symbols, M6.8's bank grant and R1c's per-class pipeline depth. It sits outside the grand total the way route (a)'s closing refinement does rather than being an item the sums reach, and stating that is what stops the `frozen` and `qualified` flags reading as though they close themselves.

The other four off-clock rows are the radio reference state machines (inventory rows 19–22), whose authoring rides the release program: they arrive with the roster the first release carries whole (R-18-004), and under R-12-043e each begins as a version-pin of the machine-checked symbolic analysis of its protocol, a transcription into the one prover, and a formal-to-formal review rather than an original reading of the prose standard. Deciding which edition of each Tamarin or ProVerif artifact serves as the row's upstream is the first task of each row's authoring and the cheapest part of it; the RRC row additionally names which procedures fall outside the published analyses and take the R-05-050 hand-transcription posture, so the thin lane is scoped before it is walked.

### Checklist conventions

* **A landed item keeps its header line, its cell, one summary line and a link, and its note lives in [the completion log](completion-log.md).** The log carries one entry per landed or struck item under a heading spelling the item's label as this document writes it, and the entry is the completion evidence the landing recorded, verbatim; the summary line here names what the item did and states no figure. K-82 holds the log's entries total against the landed items in both directions and reads the findings blocks there, K-84 reads the landing declarations there, and the link is what K-12 resolves. An open item's note stays here until it lands.
* **Exit evidence records what an item's gate measured, and two standing figures are stated only where they move**: from M0.6f the profile sweep refuses 199 of 199, and the legacy rig's agreeing prefix is 67 records on all 54 `rv64ui-p-*` members.
* **A proofs-lane item reports its own file's constant count and not the proof gate's global total.** The global figure is derived over the whole of [proofs/](../proofs/), so any lane that adds a `.v` moves it, which makes it the one exit-evidence figure a sibling landing invalidates rather than a property of the item that quoted it. The landed Gallina items already split on this without saying so, the earlier ones quoting the global and the later ones their own file's share; the later reading is the one this convention adopts.
* **Every item carries one estimate cell, and only what is inside it is authored.** An open item reads `· 6 h, range 4–8 · 0.7%`, a completed one `· 1.9 h actual · 0.2%`; the range and the actual are the estimates, in attended agent-session hours, and are re-priced when split. The rest is arithmetic: the midpoint is the mean of the range ends, and the percentage is that midpoint's share of the grand total. An item whose children carry the estimates carries none of its own.
* **Every subtotal, the grand total, its range, and the progress figures are sums over those cells**, recomputed by `tools/check.py` (`--fix` rewrites them), so a re-priced item moves everything resting on it in the same edit.
* **Every open item carries an authority class beside its estimate**, `I` where the authority it realizes is inside this repository and `X` where it is outside. The classes are priced differently because they have measured differently: over the sixty completed items carrying both an estimate and an actual, the forty-six whose authority is inside this repository ran at 0.71, and the fourteen whose authority is outside it split, the twelve that read, pin, install or measure an external thing running at 0.76 and the two that authored against an external authority at 1.68. **The 1.68 every open class-X cell is priced against is that second pool and not the class**, which is the whole of what makes n = 2 the weakness the risks table states. The fit's pools are recorded rather than recoverable, because a completed item carries its actual instead of its class, the class having done its work at the estimate: [the calibration record](#calibration-record) carries every completed attended item with its pool and the earliest estimate its cell recorded, and `tools/check.py` recomputes each ratio and count above from that record and the actuals beside it, rewriting them under `--fix`.
* **A completed item marked `agent-parallel` ran under fan-out rather than at one attention, and its actual is measured on a different clock.** Its figure is the summed agent-session wall-clock of the authoring, verification and repair passes the item took, which is not the attended figure the completed items before it were priced in. **The two series are not pooled**, and the ratio above is over the attended one alone. What the label marks is the execution mode and never the quality bar: an agent-parallel item clears the same gates, declares the same tier, and is read the same way. **The series is twenty items** (S19, S20, S21, S22, M0.20, M1.2a, M1.6, M3.2, M3.4a, M3.4d, M4.2b, M4.3, M5.1, M5.2, M6.0b, M6.2a, M6.3a, M6.4, M6.5a, I15), the count and the list being the tool's, and **the re-fit across both modes is S19's, whose ruling is that they are not pooled**: the two figures are different quantities, no item has been measured on both clocks, and nothing in this tree converts between them, so the parallel series is fitted over [a record of its own](#the-agent-parallel-series) and stated beside the attended fit rather than folded into it.
* **A lane that lands under fan-out leaves the arithmetic to the integrator.** It runs `python tools/run.py` plain and reports the drift rather than repairing it, because every landing moves the hours and the findings totals and two lanes that both repair emit conflicting figures on the same lines; the integrator runs `--fix` once per merge, as its own commit. The selftest's baseline is `check.py`, so on a lane whose arithmetic is red no mutant decides anything, and such a landing quotes no mutation figure rather than quoting one from a tree it did not land.
* **A count in a note carries the predicate it was taken with, and a figure the revision it was taken at.** Two readers counting one document at one revision can both be right and disagree, a case-sensitive pattern and a strict bullet head giving different totals, so a count is reproducible only with its predicate beside it; and a figure read off a working tree that a peer's push can move between two commands is reproducible only with its hash. F-208 is the class booked once, a search's result stated as a smaller set than the search returns.
* **The width test is set and it is a span floor: a class-X range's upper end is at least twice its lower end.** That is the *roughly a factor of two* this document already claims of every range, made a gate for the one class whose outturn says it is not decoration, and `tools/check.py` holds it. Class I carries no floor, having run under estimate.
  **The obvious threshold was tried first and is arithmetically unavailable, which is why this one is a span rather than a multiple of the midpoint.** *The calibrated value lies inside the range*, upper ≥ 1.68 × midpoint, is the test the ratio actually motivates; but a midpoint is the mean of the range ends, so that test is equivalent to lower ≤ 0.32 × midpoint and forces every class-X range to a span above five. Applied to the cells as they stand it would either drive the lower ends to a third of their midpoints or, holding the lower ends, re-price the midpoints upward by more than a factor of two, which is exactly the re-price the ratio is stated **not** to be. The two rules collide, and the span floor is what survives the collision: it is tied to the convention this document already states, it discriminates the class the measurement discriminates, and it leaves the calibrated total where it belongs, stated separately rather than folded in.
  **What the floor does not do is make the calibration a gate.** A cell can clear the span and still have a midpoint the ratio says is low, and nothing here reports that; the calibrated total is where it shows, and the 1.68 the whole convention rests on is fitted over two completed items, a count the record carries and no span widens.
* **`Wasm-parallel`** means the item's deliverable is Gallina logic needing no toolchain, no image and no machine model (§0), so its gate is the register rather than M1 and it may run in any lane from today. **The label names a validator the entry point does not carry, and the landed items say which one they used instead.** M1.5 closed the CertiCoq→Wasm loop on `demo.v` alone in a switch of its own, [tools/wasm-oracle/](../tools/wasm-oracle/) carries that file and [ipc_oracle.v](../tools/wasm-oracle/ipc_oracle.v) beside it plus a Dockerfile, a runner and a hand-run recipe, and no `run.py` command reaches any of it. **Every landing that carried the label was validated at the prover level**, through `run.py proofs` and `run.py seed coq`, as were the Gallina landings beside it that never carried it. **Staging a repository Gallina source into the Wasm oracle is priced once and it is M4.3's**, which staged `ipc_oracle.v` at 4 h actual and is the only cell that has met the label's verb at the execution level; every other cell carrying the label leaves it uncosted.
* **Landing is two-tier.** Tier A is a full attended read: any register, profile, crown-jewel, absence-contract or coverage-matrix edit; any moved co-read pair; any new normative claim; every decision item. Tier B is a spot read of the item's findings, admitted on four mechanical conditions: checker green with every mutant killed, no Tier-A edit, the co-read ledger unmoved, and a rule holding whatever fact the item created.
* **A landing declares its tier, and a Tier-B landing names what holds it.** A landed item carries one `Landed: Tier A` or `Landed: Tier B under` line in its completion-log note, the second naming in bold every rule that holds a fact the landing created. **A bolded rule id is a holder citation and a plain one is not**: a rule relied on is written in bold beside what it holds, which is the form the landed items that created one already use, and a rule merely discussed stays plain, so the document tells the two apart instead of leaving it to the reader. A holder need not be new, an existing rule whose subject a landing extends holding the new member and being named the same way. K-84 holds every holder citation to naming a rule [the registry](../tools/check-rules.md) carries and every Tier-B declaration to naming one, and it reads a declaration where it is made rather than demanding one where it is absent, a tier being a property of the reading a landing was given and not something a later hand assigns to it. What no rule decides is whether the named rule holds *that* fact, which is the residue every conferral here declares.
* **An item's acceptance predicate is authored and landed before its implementation lane opens.** M0.11 and M1.8a are the precedent and M1.8a states the reason: an instrument arriving with its own acceptance criteria has graded its own homework. In a multi-lane operation this is what lets a lane self-check, and it is the precondition for a Tier-B landing. **The five open items that owed one carry it**, authored at S18 rather than left for a lane to discover: M1.7, M4.4 and M5.3, which are on the critical chain and where the precondition is worth the most, and M6.3b and M6.5b behind the M8a gate. Where a predicate is not yet writable the cell says so and names what owes it, as M3.6b does and as three of those five now do over one of their halves, rather than staying silent. An item entered after this convention carries its predicate at entry, and one whose predicate is refused carries the refusal in the same cell.
* **Validation is generated, not authored, wherever an oracle exists.** The model-as-oracle technique is proven in this tree at 21,546 vectors (M2.1) and 658,659 vectors with twelve seeded defects killed (R1a). A hand-written corpus member where a generator would serve is a finding.
* **A fact has one owner and every other statement of it is generated.** Where an artifact restates a fact the model, the register or a contract owns, it is emitted from that owner and regenerated in the checking act. A hand-written restatement held equal by a rule is the older discipline and is a finding under this one: the rule can only tell you the two disagree, after they already do.
* `Parallel` means the item can proceed in a separate worktree and build directory.
* **`Parallel` is about the build lane and not about attention.** A linked worktree derives its own lane under `/root/build/lane-<name>/`, one directory holding that lane's build tree, iterate tree and SMT cache ([I7](#build-loop-instruments)), so two items that both write `model/` share no build tree, no log, and no emulator, and a build holds its own lane rather than the toolchain: a second `run.py model build` over a live one in the same lane is refused by name, while a sibling lane's runs beside it. **Lanes isolate files and build trees, not CPU.** The machine stays one thing, twelve cores under one WSL VM, so concurrent model work is priced in wall time rather than in correctness, and what overlaps a running build for nothing is the work that opens no lane at all: a provenance decision, a document act, or a checker rule.

### Considered and rejected

Recorded so they are not re-proposed, which is the same discipline [the alternatives register](architectural-alternatives.md) keeps for the design.

- **Lowering as a post-pass over stock `ccomp -S` output.** Wrong on this machine's own semantics: an integer write yields an **untagged** capability (M0.6e e3, R-05-136), so ordinary RV64 pointer arithmetic clears the tag on every address it touches. Rewriting each such site into a capability increment needs type information CompCert has erased by `Asm`, and CompCert deliberately conflates pointers and integers at 64 bits. The idea's residue is what M1.1b rests on: the delta is concentrated in `Asmgen` and the calling convention.
- **Cutting the rules, the mutation selftest or the co-read ledger to reduce review cost.** Backwards. That machinery is exactly what makes a Tier-B landing admissible, so shrinking it moves work back into the one lane that cannot be widened.
- **Adopting CHERIoT-Ibex for the main core.** Already correctly excluded, its distinct compressed encoding being what R-15-005's single-encoding requirement refuses.
- **Parallelizing the build further.** I5, I6 and I10 measured it: clang took the generated unit's compile down by half and the residual is Sail's own single-threaded emission, which I6 showed a compiler mode cannot reach. CPU is not the constraint. Hardware still helps, through S9's finding class rather than through throughput.
- **Deleting `model/dependencies/`.** Checked at S3's scoping; every member has a live consumer, softfloat serving the surviving vector floating point and `asio` being S11's socket layer.
- **Raising the attended-hours budget.** Not a proposal at all. It is the one input this document cannot supply.
- **A second fast emulator, a whole-system simulator, or a new proof language** without a demonstrated blocker in the existing workflow. S4 measured that no loop before M7.1 is emulator-bound, and the two-language discipline this plan opens with is what a third language would spend.
- **Shipping extracted host code and treating its native execution as evidence** for the capability, timing and hardware theorem. The host processor and its runtime become dependencies of a different assurance argument, which is Q10's reading of a host product.
- **Feeding generated integer-pointer C into the capability compiler and taking source-to-device correspondence as inherited.** M1.6 measured the reaching exit's printer carrying no theorem, so the relation at that boundary is authored or it is absent, which is the audit Q2 carries.
- **Replacing an unqualified cell with a simulator parameter and calling the memory qualified.** R-15-247m wants the measured macro with its overheads, and a constant in Sail can be the name of an unsolved analog system; Ramulator2 and OpenRAM enter Q6 as comparators and neither qualifies the proposed stack.
- **Adding up improvements that address one bottleneck, or crediting vectorization, quantization and synthesis the baseline already assumes.** Q1 and Q8 keep each alternative in an estimate scenario of its own, and the whole-program bound on a partial speedup is stated with the Q items.
- **Installing every candidate dependency now.** One experiment is selected, its dependencies are reviewed and pinned, and it answers a question before the toolset widens; Q6's two simulators and Q5's solver are conditional on the comparison and the enumeration that precede them.

Three readings sort the set. **Use more of the instruments already selected before selecting more.** Connecting a small generated implementation to the actual target, measuring a useful workload and checking the static resource assignment independently are the acts most likely to reduce effort without weakening the security architecture. **For capacity, start with less data and better placement, and change the physical topology only for a large physical gain.** Public immutable weights are the narrowest useful external-store experiment; more-transistor SRAM buys stability and voltage margin and not density; more matrix throughput does not lift a weight-bandwidth ceiling. **No figure in [the performance estimates](performance-estimates.md) rises because an item here is accepted.** Some of the repairs make those estimates less optimistic, and only a measured change against the current assumed baseline is credited, never a feature the estimates already assume.

The order is between these items and not a schedule, and a decision that rejects its option still completes the item.

It becomes separate scalar, media, masked-crypto, prompt-processing and token-generation claims, each naming its comparator and its evidence, with an unknown preserved as an unknown; the arithmetic under it stays the checker's compounds group's to hold.
  * **The overview claims are repaired at their owners, and the highlights cite nothing outside the page.** [The README](../README.md) heads its memory section *no allocator waste*, what is removed being allocator waste and not reservation fragmentation; credits exact bounds to the hardware and the offline layout together, with the install check refusing a narrowing that would round (R-15-007c, R-15-007k); says of the memory path that no history is left for timing to leak, the bank-address term and the secret-address rejection standing in its own table; defines detection inside the fault model a detector is built for; and names no shell, the injection row refusing a text shell where the command interpreter pipes typed values.   * **Record with every result** the image identity, the workload, the quality target, the memory population, the clock and power assumptions, the method and the uncertainty, and keep host elapsed time, target model cycles, FPGA observations and silicon measurements apart.
  * **Done when** a candidate can fail the product gate while satisfying every security admission rule, and every performance claim names its comparator and its evidence. The report and gate machinery already in the tree is reused, no benchmark dashboard precedes a reproducible result, and a documentation correction improves accuracy and not hardware speed.

  * **Generate the imperative output and its checked functional relation**, keep the output reproducible rather than edited, and make one small source change and regenerate to expose the maintenance cost.
  * **Audit the boundary from Bedrock2's word-and-byte memory to capability-bearing code**: pointer representation, provenance, bounds, calling convention, external calls and failure behaviour. An integer address is not turned into a capability by an unchecked change to the printer.
  * **Choose the device path explicitly**: capability-aware lowering through M1.2's backend, or a justified adaptation of the verified backend, and close the relation to the Sail model, the intermediate-language step included. A stock Bedrock2 RISC-V theorem is a theorem about another machine, and the Clight intermediate R-05-043 names is emitted by neither exit, so the route is a second front end until that bridge exists.
  * **Measure** generated code size, target cycles, peak storage, proof-build time and the hand-authored glue that remains, against the manual-refinement route, before the technique widens.
  * **Done when** one useful component has one authoritative operational source, a mechanically regenerated implementation, a checked relation at every claimed boundary, and an execution on the target model. A host-only prototype completes the first experiment and not the device proof. The CompCert-C/VST route stays the default until a comparison displaces it, and the item stops where the bridge or the backend costs more than the duplication it removes. Higher-order specification code does not fit the target subset, which M1.6 measured over the supervision tree, so nothing here is sold as compilation of the golden model; functional compilation establishes neither constant-time behaviour, resource bounds, robust preservation nor the hardware refinement; no general Gallina compiler and no verified collector is built first; the domain-specific generation already in the plan stays where it fits, and hand-refined code stays where it makes the implementation and the proof simpler.

  * **Specify and test the admitted fault model and the fail-stop behaviour at the touched hardware boundary.** [The crown-jewel inventory](crown-jewels.md) books the protected-sequence fault model as not authored, and common-mode failures are assessed before a redundant protection mechanism is added or refused.

The routes are the existing Sail, Rocq, Verilator, QuickChick, `oracle` and `seed` ones [tools/README.md](../tools/README.md) states, and a new fuzzing framework is not the first dependency wanted here. The effect is stronger evidence and less regression risk at more immediate effort: a test can falsify a claim and a surviving test discharges no universal theorem, and no speed or capacity credit belongs to this item.
* [ ] **Q4 · Measure inference demand before adding supply** · 14 h, range 8–20 · 1.1% · X

  * **Run host-side prompt-processing and generation benchmarks with machine-readable output**, then a separate end-to-end run including tokenization, sampling and first-token latency, with memory and energy taken by further instruments rather than assumed to be supplied. `llama-bench` is the host benchmark and behavioural comparator and not an admitted runtime; its own documentation excludes tokenization and sampling time, and model weights carry licences of their own, independent of the engine.
  * **Extract the selected operator behaviour and traffic demand**, then measure the corresponding target kernels and the fixed bandwidth grant. M6.8 is where the admitted token rate is derived from the bank grant at composition; this item supplies the demand side ahead of it, and a host GPU token rate is not carried into the target estimate.

* [ ] **Q5 · Search static placements within the isolation rules** · 12 h, range 8–16 · 0.9% · I
  * **Export the placement problem as structured data**: object lifetimes, alignment, representable bounds, owner, bank, memory class, reserved sizes, slot grants and timing limits, over M1.9's plan, with the memory-plan obligations (R-08-012c) and [the bank-count contract](bank-count-dse-contract.md) as the constraints.
  * **Enumerate first, over a small candidate set**, and add OR-Tools CP-SAT only where a coupled placement or scheduling search justifies it.
  * **Let the solver propose and an independent exact check admit**: every assignment is re-checked with exact arithmetic, uncertain physical costs are rounded conservatively, and the search tool never becomes the root of admission trust. The trusted admission checks keep the proof status they owe, and a Python validator is development hygiene and not that proof.
  * **Compare with the standing plan** on admitted workload, unused reservation, image padding and worst-case timing, recording the solver status: a timeout or `UNKNOWN` is not infeasibility, and `FEASIBLE` is not optimality.
  * **Optimize within the existing ownership and timing rules first.** Cross-owner borrowing or a new shared-lifetime assumption is an architecture change taken elsewhere and not a solver convenience.
  * **Done when** the same workload has a checked improved assignment, or the report says why none was found without presenting a limited search as a proof of impossibility. An optimality claim needs more than one checked feasible assignment. The gain is possibly more usable payload in the same RAM and better throughput under the same schedule, no raw capacity, and nothing at all where the present assignment is already good.
* [ ] **Q6 · Compare memory topologies on one workload** · 17 h, range 10–24 · 1.3% · X · after the M8a gate
  * **Compare three candidates on the workload each actually satisfies**: a smaller qualified all-SRAM configuration, the two-class configuration R-15-247 states, and SRAM beside an explicit public-weight store.
  * **For the public-weight candidate, stream bounded chunks authenticated against a trusted model identity**, keep authority-bearing state and the verification buffers local, import neither executable authority nor external capability tags, and specify buffering, the integrity-failure behaviour and the physical requester interface.
  * **Account for link bandwidth, verification throughput, scratch buffers, loading time, storage energy and visible access patterns.** Public weights do not make prompt-dependent sparse accesses public, and an external device can deny service, so no hard delivery is promised without a separately justified bound.
  * **Use supplied or measured physical coefficients**, ECC, tags where needed, periphery, routing, refresh, repair and thermal corners included, and ask a foundry or macro provider for realizable supply rather than literature cell density. R-15-247m wants the measured macro and R-17-063b books the stack as an offering of no foundry; R4 and R5 are where the second class's architecture and qualification evidence land, and this comparison precedes them.
  * **Decide the topology and the address-growth story while the format is undeployed.** R-15-007d freezes the width at the profile and stored authority is what makes the freeze permanent, so the decision is taken before a deployed population turns it into a migration; explicit block storage need not be mapped into the capability address space, and wider load and store addressing is a separate decision, a register act this item raises and does not take.
  * **Done when** the candidates are compared on useful workload, total resources, implementation maturity and physical threat claims, and the selected product has a credible supply path; a capacity-only winner that cannot deliver the required bandwidth loses. Ramulator2 serves a conventional-DRAM alternative and OpenRAM an SRAM macro exploration under a suitable technology setup, both conditionally: neither supplies or qualifies the proposed oxide-semiconductor stack, Ramulator's default out-of-order front end, cache and dynamic scheduling are not a model of this machine, so the trace and the controller policy are supplied, and an OpenRAM model in another process is not a scaled prediction of this one. The strongest route to much more physical storage changes the one-die realization (R-15-162) and its absence of an external memory bus, can expand accessible model data without widening directly addressable RAM, and may make a larger model possible while making each token slower.
* [ ] **Q7 · Decide bulk remanence deliberately** · 10 h, range 6–14 · 0.8% · X · after the M8a gate
  * **Decide whether abrupt-power-loss confidentiality for sensitive bulk is required for the intended deployment.** R-17-058f books the second class's remanence as a residual no construction closes, and it does not disappear behind capability-tag invalidation, which retires stale authority and not plaintext. The threat decision can be taken ahead of the rest of this item.
  * **If it is required, compare three arms**: keeping sensitive data in protected local storage, reducing the retained sensitive bulk, and an encrypted bulk path whose ephemeral key has an independently justified lifetime and destruction mechanism, R-17-059a scoping the attacker who reaches the plaintext after the key is gone.
  * **For an adversary-controlled memory interface, include authentication, freshness, address and generation binding, and atomic data-and-metadata updates**, from a defined standard construction and never a new cipher or mode.
  * **Measure** masked cryptographic throughput, metadata storage, boot and power-loss behaviour and transition latency, and keep ciphertext confidentiality apart from the access-pattern, power, live-probe and denial-of-service risks that remain.
  * **Done when** the design either has a concrete protection construction with evidence for its threat window, or the product declines the deployments needing that property. The first arm changes R-15-199, the memory path carrying no cryptography, and is a register act; the second is scope control and not hardening. The existing cryptographic proof and oracle work comes first, and a verified primitive or a masked AES block is not a verified memory-protection subsystem. The gain is a defined physical threat window closed at more area, metadata, effort and latency, with any performance benefit indirect, such as a larger conventional medium becoming acceptable.

  * **Try the static improvements first**: layout, loop transformations, bounded tiling, supported vector lowering and the fusion the profile already admits, with code size and working set measured beside cycles.
  * **For a media or arithmetic hotspot that remains, compare a bounded verified hardware operation with the software**, with state, data movement, reset, authority, constant-time obligations where relevant and proof maintenance all in the comparison.
  * **Reuse the Ara, Gemmini and OpenTitan material [THIRD-PARTY.md](../THIRD-PARTY.md) already names** where it fits, assuming nothing about an imported block's bus, DMA, timing or verification contract carrying over unchanged.
  * **Done when** the composed workload improves at acceptable quality and energy without breaking its timing and protection contracts, each architectural alternative in an estimate scenario of its own and the current-design baseline unmodified. The gain is potentially large on the accelerated fraction and not a scalar uplift; many optimizations and accelerator families are already assumed in the estimates, so implementing one realizes a budgeted benefit rather than earning it again, and a codec accelerator is not a shortcut merely because fixed-function hardware is admissible.
* [ ] **Q9 · Restore compatibility and local autonomy selectively** · 14 h, range 8–20 · 1.1% · X · after the M8a gate

**What an item here can claim is a direction, never a measured delta or an additive credit.**

| Change | Performance | Capacity | Implementation effort | Security |
| --- | --- | --- | --- | --- |
| Q1, the claims corrected and the baseline instrumented | Estimates may fall; the hardware is unchanged | Unchanged | Small setup cost, less misdirected work | Clearer claims, no new protection |
| Q2, reusable generated lowering | Uncertain; target optimization still needed | Possibly less runtime or image overhead | The strongest candidate for recurring savings | Fewer manual correspondence gaps where the whole route is checked |
| Q3, the proof and oracle instruments connected | Usually unchanged | Unchanged | More immediate work, less regression uncertainty | Stronger evidence, not universal fault immunity |
| Q4, quantization and smaller inference demand | Can help bandwidth-bound work; quality and compute trade off | More useful payload per byte, not more RAM cells | Moderate integration and validation | No automatic hardening |
| Q5, a better static assignment | Fewer waits, or more useful work fitted | Better utilization only | Solver integration plus the independent check | Isolation preserved while the same constraints hold |
| Q6, explicit external public bulk | May slow generation while improving fit | Potentially a much larger data store | A new interface, its checking and its hardware integration | A new integrity, traffic and availability boundary |
| Q7, authenticated-encrypted sensitive bulk | Usually a direct cost | Metadata consumes space; a larger medium may become acceptable | A substantial new subsystem | Better-defined physical confidentiality and integrity |
| Q8, targeted acceleration | Potentially large locally, limited in total | Area competes with RAM | More hardware integration and proof work | Neutral only after the new obligations are met |
| Q9, bounded compatibility and local workflows | Primarily usability | A resource cost, not a capacity gain | Less porting, at the cost of new interfaces | Each added trust boundary analysed |
| Q10, a smaller product scope | A better chance of meeting latency and power | Less capacity required | A large reduction in the work a useful product needs | A smaller attack and proof surface, fewer features |

For an optimization that reaches only part of the runtime, the whole-program bound is `1 / ((1 - f) + f / s)` for the fraction `f` of the original time accelerated by `s`, every other cost unchanged; added transfers or a changed schedule invalidate that simplification and are measured separately. External bulk capacity is not a token-rate gain, and compressed data capacity is not a wider physical address space.

**Candidate dependencies are consulted, and none is installed or vendored by this section.** Existing pinned components keep their licence authority in [THIRD-PARTY.md](../THIRD-PARTY.md); a new candidate needs a selected immutable revision, a dependency and notice review, and a reproducible invocation before the milestone that would incorporate it reads its terms, and a root licence covers neither bundled dependencies, PDKs, model weights nor every generated artifact. The host tools live apart from the Rocq and Sail switches, platform and interpreter compatibility is checked at the chosen revision rather than inferred from an upstream's Python API, a tool whose supported environment is Linux runs through the WSL dispatch, and an experiment that becomes recurring work enters through [tools/run.py](../tools/run.py).

**Licensing is an implementation constraint as well.** The CompCert route through SECOMP carries non-commercial terms outside its dual-licensed subset, which [THIRD-PARTY.md](../THIRD-PARTY.md) decomposes, so a permissive generator does not make a commercially usable compiler chain, and what it recovers of third-party rebuildability is exactly the components it lowers, M1.6 having recorded that the recovery reaches the allocation-light components and never the kernel. The intended use and distribution terms are resolved before a product depends on that route, and the permissive Bedrock2 route is compared without being treated as an immediate replacement, its capability target being absent.

Five shortcuts are worth taking and the section rests on them: generate implementations and proof obligations from one source where that is cheaper than hand-maintaining both, and reuse the domain-specific routes before inventing a universal one; let powerful untrusted search propose a small artifact and a simpler independently justified check admit it, so the search algorithm is never a trusted runtime; reuse host libraries as behavioural comparators and measurement tools without promising they ship; change one architectural variable per comparison and keep current-design and relaxed-design results apart; and reject an option after a small decisive experiment rather than building its whole toolchain to learn that it misses a bandwidth or proof-cost budget. The shortcuts refused are recorded under [considered and rejected](#considered-and-rejected).

  * **The re-homing delta, and the first thing it settles is the shape of the problem.** `cheririscV/` fixes no 128-bit capability *layout*: the capability is abstract in the Cerise lineage, `OCVmem : permission -> locality -> ptrofs -> ptrofs -> ptrofs -> ocsealable` (`OCapValues.v:262`), carrying base, top and address as three full-width `ptrofs` with no exponent, mantissa or compression anywhere in the directory, so the abstract state is three words wide where the footprint is two.   * **Axis 2, the permission field, is a replacement and not a narrowing.** SECOMP's is a twelve-element abstract enumeration `O | RO | RW | RWL | RX | E | RWX | RWLX | URW | URWL | URWX | URWLX` (`OCapValues.v:39-51`) ordered by a hand-written `permFlowsTo` (`:93-140`), crossed with a three-valued locality `Global | Local | Directed` (`:57-60`) under its own `locFlowsTo` (`:65-76`).   * **Axis 3, uninitialized capabilities, is the axis the calling convention rests on, so deleting it is a design act rather than a deletion.** `URW`/`URWL`/`URWX`/`URWLX` (`OCapValues.v:48-51`) are neither read- nor write-allowed (`:190-200`); a `U` capability's authority is its *cursor* rather than its bound (`CapMemory.v:280`), it reads strictly below the cursor (`:331`), stores at or below it (`:322`), and a store at offset zero advances it (`:356-373`), which is the frontier discipline the frame layout is built on. `CapMemtype.v:123-133`'s `UNINIT` access kind threads it through every load and store, 26 `PCU*` constructors carry it into the assembly (`CapAsm.v:394-421`), and `CapAsmgen.v` compiles **every** stack access through one: `Mgetstack` and `Msetstack` (`:1063-1083`), `transl_load` and `transl_store`'s stack arms (`:1115-1218`), the frame carve `PCUtoPtr_s X31 SPC SPC :: PCsbase SPC SPC X31` (`:1333-1334`), and `store_zeros_routine`'s byte-at-a-time frame zeroing (`:1275-1285`).   * **Axis 4, sealing, diverges in the field and in the authority, and axis 5's sentries diverge with it.** SECOMP's object type is `Definition seal := ptrofs` (`OCapValues.v:24`), so the otype space is the whole address space, and sealing authority is a separate seal-capability *object* holding a range and a cursor, `OCVseal : seal -> seal -> seal -> ocsealable` (`:263`), consumed by `seal_capability`/`unseal_capability` against a bounds check on that cursor (`:1480-1496`); there is no `Permit_Seal` and no `Permit_Unseal` anywhere in the directory, and `CapAsmgen.v:1374-1376` gives each *call site* its own otype by offsetting a per-compartment seal key. ## Estimate and schedule basis

* Completed estimates are actual elapsed session intervals with overlapping build waits apportioned approximately.
* Open work classes:
  * A · pinning, configuration, and mechanical curation
  * B · semantic porting and tool re-homing with differential tests
  * C · fresh systems authoring with functional tests
  * D · RTL and FPGA work
* Confidence: every open item's range spans roughly a factor of two about its midpoint, and a class believed softer is priced by widening its own items' ranges rather than by a second figure stated over the total.
* Grand total: the sum of the item cells, 1,264.1 h midpoint over a 951.1–1,577.1 h range.
* **The authority class is the calibration, and it is measured rather than assumed.** Taking each completed attended item's earliest recorded estimate, which [the calibration record](#calibration-record) carries beside the item's pool, against its recorded actual, across the sixty items carrying both, gives 228.9 h actual against 303.4 h estimated, a ratio of 0.75. The error is not uniform and in one pool it runs the other way: forty-six items whose authority is in this repository ran at **0.71**, twelve that read, pin, install or measure an external thing ran at **0.76**, and the two that authored against an external authority ran at **1.68**. Neither overrun is random. M0.8d authored FEC decoders and Keccak against FIPS 202, the ACVP vectors and TS 38.212, and its own finding is that the two defects the known-answer vectors found were both transcriptions; M0.12 authored a corpus, an assembler, a dialect table and an ELF composer from nothing, because no toolchain has one. The deepest under-runs are equally consistent, the two lowest ratios in the record being e3 at 0.13 and e4 at 0.14.
* **The ratio is a prior on range width and not a re-price of midpoints**, which is what the conventions above already require of a class-X cell, and which is what the calibrated figure states separately rather than folding in. Its own weakness is stated: n = 2 in the pool that matters. It is every completed item that authored against an external authority, every one of them overran, all for the same reason, and the consequence is asymmetric, so it is treated as a widening rather than a multiplier. **Turning the prior into a measurement is S19's, and what that item measured is why the pool has not grown**: every completed item that has authored against an external authority since the fit was taken ran under fan-out, so it is on the other clock and outside this pool by the rule below.
* **The agent-parallel series is fitted on its own record and the two fits are not pooled**, which is S19's ruling. Taking each completed agent-parallel item's earliest recorded estimate, which [the agent-parallel record](#the-agent-parallel-series) carries beside its pool, against its recorded actual, across the twelve items carrying both, gives 84.7 h actual against 154 h estimated, a ratio of 0.55: seven items whose authority is in this repository ran at **0.54**, two that read an external thing ran at **0.45**, and the three that authored against an external authority ran at **0.65**. **The pool the class-X convention rests on falls on opposite sides of one in the two modes**, 1.68 attended against 0.65 here, so pooling would not widen the class-X prior but delete it, and it would delete it on a conversion between the two clocks that no item has been measured on both of. This ratio prices no cell, which mode an item lands in not being known when the item is priced.
* **The strategy the classes imply is one sentence: move work across the authority line, and generate what is currently authored.** What has not moved is the class-X residue before the M8a gate, which is ten open cells, five of them M1.2's children, and which the gate figures above put at more than half that gate's hours.
* Horizon: at 10–20 attended hours per week, the 829 h remaining is 41–83 attended weeks and the critical chain's 104.5 h midpoint 5–10 of them, both arithmetic `tools/check.py` recomputes over the cells and the stated rate, and neither a promise.
* At that rate the M8a gate is set by the critical chain rather than by the bill, and the chain is lane 1's to release. Review capacity was the constraint beyond three lanes; the two-tier landing rule and the unattended runner are what move it, so lane count is bounded by the register acts that gate a lane rather than by attention at the end of one.
