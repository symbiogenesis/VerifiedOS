# Scalar compiler source-value contract

This contract resolves the source-value choices in [the kind handoff](compiler-kind-handoff.md#2-source-and-intermediate-value-decisions) for M1.2g-ii and its d/e/f consumers. It specifies an implementation interface and its acceptance obligations; it supplies no implemented source semantics, compiler simulation or target acceptance. [The prerequisite qualification](compiler-prerequisites.md) supplies the existing diagnostic and inhabited block-memory evidence. [The scalar ABI](purecap-abi.md) governs locations and calls.

The [requirements register](../../requirements-register.md) and its [representation and provenance prose](../../spec.md#r-05-136) take precedence. R-05-136 and R-05-137 exclude integer-to-capability provenance and exposed-address state from verified C; R-05-139 and R-05-140 exclude type punning outside the declared codec routes. This is the platform's admitted CHERI-C profile, not an assertion that all programs accepted by stock CompCert remain admissible. The [CompCert C manual](https://compcert.org/man/manual005.html) documents pointer/integer round trips and broader representation access that this profile does not admit. The contained compiler's measured cast behavior is therefore a compatibility finding to reject explicitly, not a semantic rule to preserve by losing tags.

## 1. Abstract values and the concrete boundary

Retain abstract `Vptr(block, offset)` values through the source languages and Mach. Ordinary fixed-width integers remain integer values. A source null pointer has an explicit authority-free `Null` interpretation, even if the contained frontend initially represents its syntax with an integer-zero constructor. Uninitialized or invalid source values are not null. The [kind interface](compiler-kind-interface.md) carries the distinction through operations, calls and storage; equal bit width never determines it.

Mach-to-capability-aware assembly is the lowering boundary for operations and representations, not an assignment of physical addresses. Its symbolic capability references carry block/symbol identity, byte offset, authority origin and role. The assembler/composer resolves these references using the selected memory plan and actual image. This preserves [M1.2a's recorded block-model decision](../completion-log.md#m12a-re-baseline-the-delta-against-stock-compcerts-risc-v-backend): block allocation in the semantics does not authorize a target runtime allocator, and concrete placement is the composer's act.

The implementation must define one representation relation `Rep(rho, A, v, c)`:

- `rho` is the selected composition's block and live-range placement, not an arbitrary test address map. It binds each live allocation instance to its plan region, physical base, extent, initial initialization plan and generation/lifetime. The evolving initialized-byte and memory-content relation is a separate state invariant; it does not mutate the placement map. Simultaneously live distinct allocations have the disjointness the source memory injection needs; stack activations use the admitted bounded frame layout. Reusing a physical slot in a later lifetime does not identify the two source blocks.
- `A` records the authority actually supplied or monotonically derived for this value: origin, reachable region, bounds, permissions, locality, sealing/call role and lifetime. It is a semantic/proof witness propagated with the value, not a hidden runtime provenance table and not authority inferred from the numerical cursor. Pointer type information alone does not reconstruct `A`.
- For a live data pointer `Vptr(b, o)`, `c` has the source-prescribed role and authority, and its cursor is the exact mathematical sum `rho(b).base + o`. Valid accesses correspond to the source object, its declared view, alignment and initialized bytes. The relation accounts for the abstract memory's permissions and the target's capability permissions separately; neither substitutes for the other.
- `Null` relates only to the model's null capability and carries no authority. Nullable pointer kinds therefore do not assert that every represented value has a set tag. An ordinary integer relates to its declared-width data value with no capability authority. No arbitrary untagged capability is silently identified with source null.
- A code pointer relates to its resolved function identity, admitted callee type and code authority. The ABI's ordinary unsealed code pointers, exported entry sentries and backward-edge return sentries remain distinct roles. Source casts do not mint a sentry or turn a data pointer into code authority.
- An opaque grant value `Handle(h)` relates to the sealed capability named by authenticated composition/grant-slot identity `h`, with its authority witness and declared handle role. It is not a C data or function pointer. Typed moves, permitted loads/stores and the ABI's admitted argument/result paths preserve that identity and sealed value. A signature may separately admit `Null`; absent that declaration a null handle is refused. No pointer arithmetic, dereference, raw cast or implicit unsealing is defined on `Handle`. Only the declared grant-service or exact primitive contract may consume its authority, and neither an integer slot number nor encoded bytes can construct it.

Every authority witness has a constructor from a composition-supplied input or a permitted derivation and a proof that the actual target value is its result. An existentially chosen stronger root at each access is not a representation proof. The physical target instance must be exhibited for nonempty programs; the relation must preserve returned values, memory effects, allowed observations and failure behavior, not merely low data bits.

The existing `Vcap` carrier may represent concrete target values at this boundary. Its inhabited store/reload qualification does not decide the source-value relation, define pointer arithmetic or prove a connection to Sail. A choice of constructor name supplies none of those implementations.

The initial scalar source interface admits a capability-producing primitive only with evidence that, for every admitted input, its result is represented by an existing live `Vptr` of the required role, an admitted sealed `Handle`, or `Null`. If the exact Sail operation can instead produce a non-null tag-cleared capability on an admitted input, that source program receives an explicit unsupported-lowering refusal before emission. Such a result is neither source null nor `Vundef`, even when the program would only inspect its fields afterward. This is a limit of the selected authoring interface, not a change to the primitive's Sail meaning and not fulfillment or waiver of R-05-023b's production primitive-completeness duty. M1.2g-ii owns any later extension with an abstract primitive-capability result and its complete observation, memory and failure semantics; M1.2d-ii then extends the typed realization before that source case can be admitted. Deliberately mutated target artifacts still exercise the actual tag-clear behavior under M1.2f's controls.

## 2. Conversions, null and address observations

| Source operation | Selected interpretation and acceptance |
| --- | --- |
| Qualifier change or compatible object-pointer conversion, including an object pointer through `void *` and back | Preserve block, offset and authority witness exactly. Respect alignment, effective type, lifetime and the target type's allowed accesses. A cast neither broadens bounds/permissions nor permits a load at a foreign stored type. |
| Conversion between function pointer types | Preserve the capability value; a subsequent call still requires the actual function's compatible ABI and typed callee-set evidence. Object/function cross-casts are unsupported in this scalar profile. |
| Null pointer constant in a pointer context | Recognize the source-language null constant before kind erasure and elaborate to `Null`. This includes supported constant-expression zero forms, not a runtime integer that happens to contain zero. Pointer initialization, assignment, argument passing and comparison share this rule. |
| Pointer to boolean or equality with null | Decide nullness at the source interpretation and preserve it at the target. A live capability with cursor zero is not null; an integer compare of the cursor with zero is insufficient. |
| Raw pointer-to-integer C cast | Refuse in this profile. It is neither a tag-preserving copy nor an implicit address-extraction primitive. No optimizer may accept the cast and then erase its authority distinction. |
| Explicit address observation | Bind the profile's `cgetaddr` primitive to its Sail meaning. Its result is an ordinary unsigned address integer, with no provenance and no inverse conversion. For `Vptr(b, o)` the source observation is `rho(b).base + o`, represented at the primitive's output width; for `Null` it is the model's null cursor. This is a composition-parameterized observation, not the bits of a packed capability. |
| Integer to pointer, integer bit pattern to capability, or an address literal as device authority | Refuse under R-05-136. A matching address in `rho`, including one just observed from a pointer, confers no authority. The frontend's null-constant rule is not a general integer conversion rule. |
| Explicit cursor derivation from a capability already held | Use the named profile primitive with its actual capability input and Sail preconditions/effects. The integer supplies only a cursor/offset. It does not choose an ambient root or revive a tag, and the resulting authority remains derived from the supplied capability. Its admitted result must satisfy section 1's live-pointer/null representation condition; otherwise this scalar lowering is refused. This is not a C integer-to-pointer cast. |

`intptr_t` and `uintptr_t` are **not provided as round-trip types by the selected scalar source profile**. Its target headers omit these typedefs and their corresponding limit macros rather than aliasing them to ordinary 64-bit integers while implying that pointer conversions work. A source package requesting their pointer-round-trip contract is refused as unsupported before lowering, even if a host header happens to declare the names. No provenance-carrying integer kind is introduced. A future promise of these conversions requires resolving R-05-136/R-05-137 at their owners first, then extending source semantics, the kind interface and acceptance together. This restriction must appear in the emitted source-profile identity and compatibility diagnostic; it cannot silently change the meaning of a previously accepted source package. Ordinary integer-only uses do not authorize pointer conversions through a typedef.

The source semantics of address observation is parameterized by the same immutable `rho` as final composition. The source-to-target statement quantifies over admitted maps and is instantiated at the emitted image's actual map. An optimization that assumes that a pointer's integer observation is independent of placement owes that proof or is refused. Neither this parameter nor the result of `cgetaddr` adds exposed-address reconstruction state.

## 3. Pointer arithmetic and comparison

Pointer addition/subtraction by an integer scales by the pointed-to type's size and preserves the source allocation and authority witness. The source operation and its integer scaling remain explicit; integer `add` is never substituted for a capability cursor update. The admitted operation has range evidence for its source-defined result, including a one-past position where the source permits it. A one-past pointer is not dereferenceable. A step outside the admitted object/view, overflow in offset scaling, an unrepresentable cursor or a sealed operand cannot be justified by silently wrapping, widening bounds or clearing a tag and continuing.

The lowering obligation includes the actual [Sail cursor operations](../../../model/model/extensions/CHERI/cheri_insts.sail) and [representability helpers](../../../model/model/core/cap_common.sail). The target has a bounded address field; a source-valid endpoint that placement makes unrepresentable is a composition refusal requiring a different placement, not newly invented source undefined behavior. In particular, an allocation needing a one-past cursor at the address-space ceiling needs a placement that avoids that case. `cincoffset` and `csetaddr` have different helper paths; a proof about one is not transferred to the other by mnemonic similarity.

Equality preserves the source comparison judgment, including pointer/null and same-object comparisons. Same block and offset compare equal even when two permitted authority views carry different bounds or permissions. Thus the capability's full-field equality primitive `cseqx` is not the general implementation of source pointer equality. Distinct live source objects whose comparison is defined must remain distinct under the representation relation. Comparisons involving one-past pointers, adjacent objects and reused storage require the selected source semantics' validity premises and the corresponding placement/lifetime proof; physical cursor equality alone is not that proof.

Relational comparison and pointer difference are admitted only with the source-defined object/array and validity premises. Difference returns an integer count of elements, with exact divisibility by element size and representability in the selected `ptrdiff_t`; `csub` returns a byte difference and does not establish these premises. No ordering of unrelated objects is invented from physical addresses. If an operation is defined by the selected source semantics but the scalar lowering cannot preserve it, it receives an unsupported-lowering diagnostic, rather than being reclassified as source undefined behavior.

Ordinary integer operations retain their selected source semantics. Admission separately enforces [R-05-144 through R-05-147](../../spec.md#r-05-144): explicit width/signedness changes, range evidence for ordinary arithmetic, and explicit named modular or saturating forms where intended. The compiler may not use the underlying C model's broader arithmetic behavior to waive those obligations. Offset arithmetic and pointer differences are covered by the same rule.

## 4. Memory, copies and destructive overlap

Every memory operation identifies both its address kind and its **payload** kind. A load through a capability may load an integer or a pointer; the address being a pointer does not select the payload operation. Pointer objects, typed argument slots, spills and return links use the capability-preserving memory operations at the model's alignment. Integer objects use scalar operations. Object layout keeps capability slots separately identified even when an integer slot has the same byte width. The kind distinction must survive the diagnostic's first losing boundary before `Cshmgen` maps equal-width accesses to one chunk.

Source pointer storage preserves the abstract pointer and its authority witness. Concrete `lc`/`sc` traffic preserves the encoded value and tag, subject to the address capability's permissions, locality and lifetime rules. A local capability can be stored only through the ABI's stack authority bearing store-local. A source assignment to an impermissible destination is an admission failure; the compiler cannot clear the tag to make the store succeed.

The selected copy rules are:

| Copy or write | Required behavior |
| --- | --- |
| Pointer assignment, move, spill and reload | Preserve the complete pointer/authority value with capability operations. Mixed pointer/integer live values need separate kinds even when physical registers or dead slots are reused. |
| Copy of declared typed objects, including a `memcpy`-shaped intrinsic with proved disjoint ranges | Copy each pointer field as a whole capability and each non-pointer field at its declared kind. Source/destination layouts, offsets and alignment are fixed or proved by the source contract. Preserve initialized fields without inventing readable padding. The intrinsic is a typed operation, not permission for source byte loads from pointer storage. |
| Overlapping typed copy with a `memmove`-shaped contract | Preserve the pre-copy source values through a proved traversal order or bounded temporary slots in the existing plan. Whole capability fields retain their tags. Overlapping `memcpy` inputs do not acquire `memmove` semantics. A partial or misaligned capability-field overlap lacking a typed interpretation is refused. |
| Copy of actual byte buffers | Preserve bytes through the scalar byte operations. It grants no authority and cannot transport or reconstruct a live pointer. Generated codecs remain subject to R-05-140 and cannot synthesize capability authority from encoded bytes. |
| Scalar or partial write intersecting a capability granule | The physical write clears that granule's tag, even if its data bytes happen to be unchanged. Unaffected granules preserve their tags. This is a destructive target effect, not a valid implementation of source pointer assignment. |
| Reading pointer storage at an integer/byte type, unions or reassembling a pointer from scalar pieces | Refuse the source or its derivation under R-05-139/R-05-140. An untyped copy with no complete payload layout is not admitted by guessing kinds from runtime tags. |

A target mutation that replaces a pointer spill with an integer store has an explicit sequence: the write clears the tag; a later capability reload supplies an untagged value; its attempted authority use has the Sail-defined failure. The write itself does not have to trap. A destructive byte write followed by scalar restoration of the original bytes does not restore the tag. An independent surviving capability may be stored later by a genuine capability store if its destination permits that operation; this is replacement from held authority, not bit-pattern reconstruction.

The source abstract-memory result after a prohibited overwrite may be invalid or undefined under the selected model. It is not equated to every target untagged value and supplies no theorem that malformed memory loads return source null. M1.2g-i's fragment/overlap tests and their reported `Vundef`/integer-zero distinctions remain logical-memory evidence. M1.2g-ii owes the physical tag-clear connection and M1.2f its actual emitted target controls.

## 5. Refusal boundaries and acceptance

The implementation records source site, operation, profile/plan identity and one of these distinct outcomes:

- **Unsupported source/profile:** a construct outside the selected profile, such as a pointer/integer round trip or type punning. Reject before kind erasure, including inside inlined helpers and dependency headers. Do not silently produce ordinary RV64 code.
- **Unproved source/admission premise:** missing initialization, lifetime, effective-type, range or comparison evidence. This is not a target trap and not an automatic claim that the source program is undefined.
- **Unsupported lowering or invalid composition:** a source-defined operation with no justified emission, missing kind/authority, bad alignment or unrepresentable placement. Reject the producer package or composition at the owning boundary; do not weaken its source contract.
- **Architectural target failure:** the specified Sail result of deliberate invalid capability use or corrupted output. Keep cause, timing and side effects distinct from compile/admission refusals. Ordinary admitted positive cases cannot satisfy functional acceptance by trapping.

M1.2g-ii implements the selected source relations and memory connection; M1.2d-ii preserves their kinds, authority references and copy/call behavior; M1.2e-ii checks actual narrowing provenance where derivation requires it; M1.2f exercises their real compiler output. Acceptance includes all of the following nonempty populations with source/configuration/image identity and predeclared observations:

| Population | Decisive positive and refusing or destructive neighbor |
| --- | --- |
| Values and conversions | A live pointer, a distinct full-width integer and `Null` survive typed local/argument/result paths. A pointer through `void *` returns with its authority; address observation equals the selected placement. Dynamic integer zero, nonzero literal, observed-address reconstruction and an `intptr_t` round-trip request are rejected at the selected source boundary. |
| Arithmetic and comparison | Array interior advance, return from one-past, element difference, pointer/null and permitted differently bounded views are exercised. Generated range/end-of-space and sealed-operand controls expose unsupported placement or misuse; a source primitive program intentionally producing a non-null tag-cleared result is refused as unsupported lowering rather than assigned null/undefined semantics; equality tests distinguish address comparison from full capability equality. |
| Memory and calls | Actual compiled pointer and integer payload copies, mixed values live over nested calls and stack arguments beyond the register set execute. Pointer stores retain tags; integer stores do not gain them. Typed disjoint and overlapping copies include more than one pointer field and distinct values so a dropped or reversed field cannot pass. |
| Destructive writes | Generate every intersecting byte position from the actual capability granule, a whole integer overwrite, unchanged-byte overwrite and scalar byte restoration. Preserve adjacent granules. Confirm tag loss and the subsequent Sail authority-use failure; a scalar spill mutation must reach the target observer rather than fail solely at assembly parsing. |
| Authority and identity | A writable global and stack-derived pointer use their real supplied roots. Substituted code-only, wrong-region or stale-lifetime authority cannot satisfy `Rep`; an integer numerically equal to a valid address gains none. Changed layout or emitted bytes invalidate the dependent evidence. |

The tests compare source outcomes with capability-aware IR and the composed Sail execution, including authority and observable memory effects. Actual source constants and proof dependencies are assumption-audited and kernel-checked. The semantic refinement over the admitted operations, source-memory injection and authority witnesses remains to be proved; this contract neither supplies it nor replaces it with finite examples. The existing [compiler-route endpoint](../../languages/compiler-route-contract.md#equivalent-artifact-endpoint) retains final-artifact, TAL, deeper proof and arbitrary-context obligations at their existing owners. No target measurement, production compiler completion or register discharge follows from accepting this document.
