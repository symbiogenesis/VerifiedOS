**Findings**
1. [DONE] **Critical: subtree revocation is currently unimplementable.** The authority model requires a revocation colour stamped into each capability, but the frozen 64-bit format allocates all 64 bits and contains no colour field. The repository’s own CHERI audit identifies this directly in `cheri-todo.md:73-78`; compare the required mechanism in `verification-maximal-os.md:627-638` with the field layout in `isa-profile.md:134-151`. Until this is resolved, the claimed use-after-free and bounded-revocation closure is not coherent. Colour and epoch exhaustion/reuse semantics are also unspecified.

2. **Critical: several capability-integrity semantics remain undefined.** The profile does not settle tag-clearing versus trapping on invalid derivation, capability exception reporting through `mcause`/`mtval`, or whether the register file is merged. It also fails to state that vector stores clear tags on overwritten granules, leaving an interpretation under which ordinary vector data could retain a stale valid capability tag. These are collected in `cheri-todo.md:79-94` and `cheri-todo.md:135`. These affect fault handling, context sanitization, WCET, and capability forgery, not merely documentation.

3. **High: the ISA freeze has a circular prerequisite.** The profile must be frozen before Sail and the compilers and supposedly has “no build prerequisite” (`requirements-register.md:4769-4774`). Yet the dictionary, operand forms, and optional bitfield instructions are selected from actual backend output and a composed image (`isa-profile.md:54-62`, `requirements-register.md:3282`). Use two named stages: a provisional standard baseline, then one measured final freeze after the compiler and representative corpus exist.

4. **High: the proof target is still behind the architecture.** Only 1 of 22 crown-jewel specifications is authored, 3 are partial, and 18 are absent; the seven theorem targets cannot start without them (`crown-jewels.md:96-98`). Most importantly, the machine-checked statement of theorem `T` and its seam interfaces is itself a promised day-one artifact but absent. Further ISA and subsystem refinement before that statement risks optimizing for a proof whose interfaces later do not compose.

5. **High: “mobile/laptop class” remains conditional and unfalsifiable.** First parts have 1–2 GB, while a phone requires 8–16 currently speculative sequential-3D tiers; the browser is deferred while cellular certification is on the first-release critical path (`verification-maximal-os.md:2626-2656`). There is no absolute product workload or latency/power floor (`critique.md:84-88`). Meanwhile estimated general interactive performance is 30–55% of a conventional core, browser code loses 60–90%, and video/GPU paths lose 70–95% (`performance-estimates.md:83-98`). Either define this as a 1–2 GB secure appliance or add measurable mobile acceptance criteria.

6. **High: the cache deletion depends on an unauthored physical premise.** Reticle-scale, potentially multi-tier SRAM is assigned one uniform access-latency constant, and that assumption justifies removing every scalar local-memory tier and cache (`verification-maximal-os.md:1862-1876`). The actual latency magnitudes are not authored (`crown-jewels.md:47`). “Deterministic” does not imply “fast.” A static hierarchy of capability-visible local SRAM and slower shared SRAM, with fixed per-region latency classes, would retain deterministic WCET without padding every access to a global worst case.

7. **High: package installation conflicts with build-time composition.** The component graph is fixed at build time and no runtime compartment may be created (`verification-maximal-os.md:140`, `verification-maximal-os.md:572`), but package installation performs capability wiring and rebuilds graphs with package-supplied nodes (`verification-maximal-os.md:1000`, `verification-maximal-os.md:1147-1152`). Define installation as either an atomic next-boot system recomposition or binding code into explicitly pre-proved empty slots. The current lifecycle specifies neither.

8. **Medium: two README bug-class closures are stronger than the normative design.**
   - Integer overflow is not universally admission-rejected. Tier-2 apps omit representation/range obligations, and runtime-dependent bounds descend to release-time proofs that no longer cover installed apps (`verification-maximal-os.md:1170-1174`, `verification-maximal-os.md:2410-2413`).
   - Relevance typing prevents dropping a verdict but allows examining a failed attestation and proceeding anyway (`verification-maximal-os.md:2400-2402`). That contradicts the stronger impression in `README.md:103-104`.

9. **Medium: mutable user-data rollback is not merely availability for every app.** A physical attacker may restore any authenticated old volume; only a fixed platform-state list receives freshness protection (`verification-maximal-os.md:833-838`). Stale payment state, revocation lists, one-time operations, or application counters can have security consequences. Add a small quota-controlled, app-facing freshness service and a `Fresh` durable-state type; keep bulk storage explicitly rollbackable.

**Radical Simplifications**
- Build a scalar “VerifiedOS Core” first: upstream-compatible CHERI semantics, canonical 32-bit instructions, one kernel instance, one ring, one storage reader, and no matrix, FEC, cellular, dictionary encoding, or narrowed bespoke capability format. Add each only after a measured failure of a stated product requirement.
- Extend the existing per-session capability-index model to all revocable cross-domain authority. Keep raw CHERI capabilities local or linearly transferred; revoke service handles by one generation-table update. This could eliminate revocation colours, the per-load filter, global sweeps, and quarantine for the common case.
- Keep only the TAL checker on-device for ordinary apps. Make source-correspondence proofs optional or Tier-0/1-only and check deep CIC proofs off-device at release. Currently every install invokes a large CIC kernel merely to prove that bytes match included source, which still may be malicious (`verification-maximal-os.md:1190-1198`).
- Retain the small verified integrity reader and A/B transactor, but initially implement the wholly non-TCB filesystem in contained safe Rust. The four fresh filesystem proof programs can follow once an availability or semantic-correctness requirement justifies them (`verification-maximal-os.md:827-836`).
- Decide the product fork explicitly: preserve single-die SRAM and target an appliance, or accept authenticated external/bonded memory for a mobile product. The latter adds one verified memory-security boundary but may remove the speculative materials dependency and much of the capacity-driven ISA complexity.

The concrete closeable classes still open are stale-authority revival, stale capability tags after non-capability writes, capability-fault misclassification, wrong responses to failed verdicts, runtime-dependent Tier-2 overflow, rollback of security-sensitive app state, and non-atomic package recomposition. Analog power/EM leakage, human consent, protocol-standard flaws, and fail-closed denial are already honestly recorded as residuals rather than overlooked bugs.
